# Тестовые стенды и диагностические программы

Этот справочник нужен при сопровождении существующего нативного теста, а не при написании
обычного игрового поведения. Эти API работают с явно смонтированными тестовыми композициями.
Подготовку сценария и оценку результатов описывает
[руководство тестирования](../../manual/testing/native-scenarios.md), а вызов —
[программы автоматизации](../../manual/automation/programs-and-diagnostics.md).

## Выберите стенд

| Задача | Контекст | Подготовка на стороне хоста |
| --- | --- | --- |
| Сбросить или изменить образец стыковки панелей редактора | `DockContext` | Подходящая диагностическая композиция редактора |
| Проверить проекцию панелей проекта | `NativeProjectionContext` | Смонтированный стенд проекции канонического тестового проекта |
| Подготовить образец элемента управления или проверить поля UI | `AppContext` | Смонтированный хостом образец каталога или Inspector |

Все эти регистрации доступны только в debug. Общие ожидания, значения и логи описывает
[общий runtime](runtime.md), ввод и захваты — [автоматизация приложения](application.md).
Маркеры областей и привязки из тестов runtime не являются поставляемым API.

## Только именованная диагностика docking

Декларации:
[editor.d.luau](https://github.com/kedra-engine/kedra/blob/main/crates/kedra_editor/types/editor.d.luau)
(English). Привязки: `crates/kedra_editor/src/workspace/fixture.rs::script_api`.

`DockContext` — альтернативный `AppContext & {dock: DockApi}`, а не
расширение, автоматически присутствующее в `EditorContext`:

```luau
ctx.dock.state: () -> DockDiagnostic
ctx.dock.reset: () -> ()
ctx.dock.drafts: () -> ()
ctx.dock.overflow: () -> ()
```

`state` возвращает `{ready=false}` или `{ready=true,generation=number}` диагностического
стенда, **не** всё рабочее пространство. `reset` сбрасывает стенд; `drafts`
переключает видимость его черновиков; `overflow` применяет заданную в исходниках композицию
переполнения. Нужна подходящая смонтированная диагностическая композиция; возможны ошибки
подготовки или неготовности. Это не общие команды стыковки панелей проекта.
Выполненная синхронная подготовка не откатывается при ошибке.

Декларация задаёт минимальную диагностическую форму, а не полную схему протокола.
`crates/kedra_editor/src/workspace/fixture.rs::describe` также возвращает `error` без
готовности и дополнительные поля готовности, идентификаторов и рендерера при готовности.
Дополнительное поле `host` и элементы массива `fields` — десятичные строки ID сущностей,
не числа Luau или дескрипторы сущностей. Схема, поколение и счётчики остаются числовыми. Эти
наблюдения не расширяют объявленную диагностическую возможность и не дают общих команд редактора.

`script_api` устанавливает эти поля только для `dock.reset`, `dock.drafts`, `dock.overflow`.
Их исходники импортируют явно допущенный `src/workspace/fixture/helpers.luau`.
Регистрация сама не монтирует и не запускает их.

## Projection API только этого стенда

Декларация:
[projection.d.luau](https://github.com/kedra-engine/kedra/blob/main/tests/fixtures/test_project/types/projection.d.luau)
(English).
Реализация привязок проекта:
[scripting.rs](https://github.com/kedra-engine/kedra/blob/main/tests/fixtures/test_project/src/docking/scripting.rs)
(English).
Привязки: `tests/fixtures/test_project/src/docking/scripting.rs::bindings`.
Эта область определена проектом, доступна только в debug и объединяет `AppContext` и
`{projection: NativeProjectionApi}`. Это не общий runtime или доступ редактора.

```luau
ctx.projection.state: () -> NativeProjectionState
ctx.projection.move: (name: string, target: string,
    edge: ("left" | "right" | "top" | "bottom")?, index: number,
    fraction: number?) -> ()
ctx.projection.maximize: (name: string?) -> ()
ctx.projection.visibility: (name: string, target: string, visible: boolean) -> ()
ctx.projection.restore: () -> ()
```

| Функция | Значение и ошибки |
| --- | --- |
| `state` | При загрузке `{mounted=false,projected=false}`; сбой исходника, запуска или UI вызывает ошибку |
| `move` | Находит живые представления по уникальному виду; цель должна быть видима; модель проверяет команду |
| `maximize` | Разворачивает группу видимого именованного представления; nil восстанавливает полное дерево хоста |
| `visibility` | Скрывает представление или показывает с индексом 0 в группе видимой цели |
| `restore` | Восстанавливает исходную топологию с сохранением содержимого/черновиков; проекция ждёт обновления |

Размещение вкладкой требует nil в edge/fraction и нативный индекс `usize` от нуля, не индекс
массива Lua. Размещение у края требует поддерживаемую сторону и конечную долю в `(0,1)`;
привязка всё равно требует `index`, но не использует его для размещения у края. Неизвестные
или неоднозначные имена, скрытые цели, отсутствие монтирования и отказ модели вызывают ошибку.
При скрытии `target` всё ещё обязательная строка, но поиск цели не выполняется.
Операции синхронно меняют модель; `projected` становится true только после проекции её ревизии.
Результат команды сам не подтверждает нативный ввод или отрисовку.

Смонтированный `NativeProjectionState` содержит `mounted=true`, `projected`, `snapshot`, `views`.
`snapshot` содержит `version`, `hosts`, `nodes`, `views`, `hidden` с Group/Split
формами топологии, как в [наблюдениях редактора](editor.md#структура-workspace).
Каждый `NativeProjectionView` содержит `id`, непрозрачную строку сущности `content`,
UI-метку `tab` и `group`, допускающие null, и `hidden`.
Это наблюдения, не дескрипторы сущностей.
`NativeProjectionAction` объявляет `reorder`, `split`, `activate`, `maximize`, `visibility`,
`restore`; публичной функции `ctx.projection.action` нет.

Rust регистрирует `projection.exercise` и Sequence для каждого действия, импортирующие явно
допущенный `scripts/Native/projection.luau` через `@game/Native/projection`.
Допущенный `.luaurc` проекта связывает `@game` с `scripts`; поиска на диске нет.
Полный сценарий находится в этом модуле; это не общий API игрового UI.

## Другие программы редактора и границы

- `catalog.prepare` (`src/catalog/prepare.luau`) получает только `AppContext`;
  образец монтирует хост. Универсального `ctx.catalog` нет.
- `inspector.presentation` (`src/diagnostics/values.luau`) тоже получает только привязки
  приложения. Проверяет префиксы полей стенда и элементы UI, а не даёт общий API
  редактирования Inspector.
- `editor.startup.forms` использует `src/scripting/startup.luau` с
  [наблюдениями редактора](editor.md).

Эти пути относительны к `crates/kedra_editor`. Имена программ — нативные регистрации,
не автоматически обнаруженные файлы проекта.
[Руководство редактора](../../manual/editor/index.md) описывает инструменты
без изменения исходников.

## Свидетельства и ограничения

Канонический проект — тестовый стенд и пример потребителя, не поставляемый игровой SDK.
Его зависимости только от runtime показывают отделение от редактора; собственный debug API
проекции не доступен автоматически любой игре. См.
[контракт стенда](https://github.com/kedra-engine/kedra/blob/main/tests/fixtures/test_project/README.md)
(English). Его геометрия и текстуры созданы Kedra, а не импортированы из частной игры;
включённый шрифт Inter сохраняет уведомление OFL. Справочник не заменяет эти обязательства.

Тесты runtime и операций Bevy проверяют отзыв и маршрут событие → изменение из дочерней Sequence
без рендерера. Тесты проекции в `src/docking/scripting.rs` отличают ещё не смонтированный стенд
от сбоя исходников/UI. Эти тесты без окна не проверяют физический ввод или отрисованные кадры;
для этого запускайте отладочные сценарии стенда. Стенд не предоставляет плагин редактора,
диагностический транспорт в release, Save, Play или песочницу для враждебного кода.
К примеру удалённой диагностики стенда также относится
[оговорка геометрии](limitations.md#геометрия-тестового-стенда).
