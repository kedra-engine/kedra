# Обработка и проверка ассетов

Этот процесс превращает инициализированные исходники в поставку и отдельно проверяет её.
Запускайте примеры из корня репозитория с доступным инструментарием Rust проекта.
Обработка работает без окон: она не открывает редактор и не выполняет код проекта.

Перед запуском команд разберитесь в различии
[исходников и поставок](index.md#исходники-поставки-и-загруженные-ресурсы).
Требования к сборке и первый запуск редактора описаны в
[Начале работы](../getting-started/index.md).

## Инициализация собственных исходников

Для нового дерева исходников выполните `assets init SOURCE` перед сборкой. Команда создаёт
недостающие `.meta` рядом с исходными файлами. Проверьте их и храните вместе с исходниками.
Существующие метаданные не заменяются, даже если настройки в них некорректны.
Каждый новый файл метаданных публикуется независимо; при сбое уже созданные файлы могут
остаться на месте. Повторная инициализация сохраняет их, не назначая эти идентификаторы заново.

Деревья `assets/editor` и `tests/fixtures/test_project/assets` уже содержат метаданные.
**Не инициализируйте и не меняйте эти канонические тестовые данные ради примера.**
Для экспериментов с исходниками используйте полную отдельную копию.
Синтаксис команд можно посмотреть без записи:

```sh
cargo run -p kedra -- assets init --help
cargo run -p kedra -- assets build --help
cargo run -p kedra -- assets verify --help
```

Инициализация не преобразует форматы. Неизвестные расширения получают метаданные `Ignore`;
реальные значения по умолчанию описаны в [поддерживаемых форматах](supported-formats.md).

## Сборка новой поставки

**Выходной каталог не должен существовать**, даже если он пуст. Его родитель может существовать.
Для каждой следующей сборки выбирайте новое имя: команда не перезаписывает старую поставку.
Корни исходников и результата не должны пересекаться: ни один не может содержать другой.
Не размещайте поставку внутри `assets/`.

Соберите ресурсы редактора:

```sh
cargo run -p kedra -- assets build assets/editor target/documentation/examples/assets/editor-delivery --namespace editor
cargo run -p kedra -- assets verify target/documentation/examples/assets/editor-delivery
```

Отдельно соберите готовый тестовый проект:

```sh
cargo run -p kedra -- assets build tests/fixtures/test_project/assets target/documentation/examples/assets/project-delivery --namespace game
cargo run -p kedra -- assets verify target/documentation/examples/assets/project-delivery
```

В обоих примерах намеренно используется профиль по умолчанию `editor-desktop`.
Он же требуется для явной привязки поставки к превью проекта в редакторе.

Параметр `--namespace` обязателен для сборки. Он задаёт логический источник для проверки
ссылок в поставке, например `editor` или `game`. Допустимы 1–64 ASCII-символа: буквы,
цифры, подчёркивания и дефисы. Параметр не переименовывает авторские ссылки автоматически.

Значение `--profile` по умолчанию для сборки и проверки — `editor-desktop`. Сейчас это точная
метка совместимости манифеста, **а не выбор размера изображений, сжатия или платформы**.
Сборка принимает непустую метку длиной до 64 байт; проверке нужна та же метка.
Приложение может использовать `game-desktop`, если ожидает такую метку, но она не делает
поставку совместимой с текущей привязкой превью проекта в редакторе.

Для отдельного приложения, явно ожидающего `game-desktop`, инициализируйте только новое
собственное дерево исходников, затем соберите и проверьте с тем же профилем:

```sh
cargo run -p kedra -- assets init /absolute/path/to/game/assets
cargo run -p kedra -- assets build /absolute/path/to/game/assets target/game-assets --profile game-desktop --namespace game
cargo run -p kedra -- assets verify target/game-assets --profile game-desktop
```

`target/game-assets` должен быть новым результатом, не существующей поставкой. Этот пример
отдельного приложения не является рецептом привязки `--project-assets` редактора.

## Что проверяет сборка

Сборка составляет перечень исходников и метаданных, отклоняет некорректные или повторяющиеся
идентификаторы и запускает нативную обработку Bevy в новом каталоге транзакции. Затем она
загружает ассеты поставки и их зависимости через источник с проверкой манифеста.
Для сцен и префабов также проверяется композиция каталога. Перед публикацией сборка снова
проверяет хеши исходников и метаданных, чтобы выявить изменения данных или состава файлов.

Опубликованная поставка содержит обработанные файлы, метаданные загрузчиков `.meta` и
`kedra-assets.json`. Этот маркер записывается последним, после проверки. Ошибка файловой
системы на этапе итогового копирования может оставить неполный выходной каталог.
Без корректного маркера это не готовая поставка. Выберите новый путь, а не используйте
такой каталог повторно.

До создания выходного каталога сборка проверяет размер сериализованного манифеста:
он не должен превышать 64 КиБ. Для большего набора исходников может потребоваться изменение
формата или ограничения размера, согласованное с разработчиками Kedra. Нельзя публиковать
поставку, которую загрузчик не сможет прочитать.

Не меняйте исходники во время обработки. Статические символические ссылки и специальные
файлы, в том числе метаданные, отклоняются. Эти проверки не создают песочницу ОС,
защищающую от конкурентной подмены файлов. Текущая сборка каждый раз создаёт чистую
транзакцию и не обещает повторное использование инкрементального кеша. Тайм-аут обработки —
60 секунд, нативной проверки зависимостей — 30 секунд. При сбое выводится диагностика,
а заведомо некорректная поставка не публикуется.

## Что подтверждает отдельная проверка

`assets verify ROOT` не записывает файлы. Команда проверяет формат и профиль манифеста,
идентичность, пути, заявленные размеры, хеши SHA-256 и соответствие записей загрузчиков
обработанным метаданным. Она **не** повторяет нативную загрузку зависимостей и проверку
композиции из сборки, не сравнивает поставку с текущими исходниками, не рисует кадры
и не подтверждает подлинность издателя. Поэтому корректная старая поставка может пройти
проверку, но не соответствовать исходникам в редакторе.

Для диагностики лучше указывать `ROOT` явно. Если он не задан, поиск использует `--assets`,
затем `KEDRA_ASSETS`, затем платформенное расположение ресурсов рядом с исполняемым файлом.

## Превью редактора требует совпадающих исходников {#editor-previews-need-matching-sources}

Привязки `--assets` редактора и `--project-assets` проекта обслуживают разные источники.
Для второй нужны явный корень проекта, пространство имён `game` и профиль `editor-desktop`.
Open не собирает ресурсы и не инициализирует метаданные. После изменения исходников или
поставки выполните сборку в новый каталог и перезапустите редактор с ним для смены привязки.

При Open пути, идентичность и хеши документов должны совпадать с принятым снимком исходников.
Каждый ресурс поставки, не являющийся документом, также должен совпадать по пути,
идентичности и байтам. Это позволяет использовать PNG, GLB, CSS, шрифты и документы
с сохранением исходных байтов, но не произвольный результат обработки. В частности,
обработка SVG для runtime работает, однако разные байты исходного SVG и результата
не удовлетворяют этому профилю превью без поддержки происхождения обработанных данных.

Отсутствующие или устаревшие ресурсы дают диагностику; навигация по принятым исходникам
сохраняется. Прямые превью PNG и статического GLB — просмотр только для чтения,
а не выполнение игры или редакторы ассетов. Для загрузки поставки в собственном приложении
зарегистрируйте её до `AssetPlugin`, установите нужные нативные загрузчики и удерживайте
дескрипторы потребителей. Сам по себе `KedraAssetsPlugin` не устанавливает все загрузчики
Bevy. Приложения, загружающие модели, должны явно включать `model-support`.

См. [ограничения форматов](supported-formats.md) и
[восстановление после ошибок](troubleshooting.md).
Управление готовым превью описано в [Scene View](../editor/scene-view.md).
Об интеграции сцен в собственное приложение читайте в разделе
[Загрузка и жизненный цикл](../scenes/lifecycle.md#подготовьте-приложение).
