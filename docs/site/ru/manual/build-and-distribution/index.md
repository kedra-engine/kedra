# Сборка и распространение

Для точных API сборщика и runtime используйте [руководство Rust API](../../api/index.md)
вместе со сценариями CLI этой главы и контрактами распространения из репозитория.

Отдельное приложение — это обычный исполняемый файл Rust с ресурсами, необходимыми ему
вне дерева исходников. Локальная для проекта команда `cargo kedra` компилирует приложение,
готовит проверенную поставку ресурсов и создаёт сборку для запуска. Отдельная команда
создаёт нативные установочные пакеты и переносимые архивы.

Для инструментов сборки не нужен установленный редактор. Это не кнопка Build в редакторе,
не генератор игр и не реализация Play.

## Выберите подходящую отправную точку

В репозитории есть три разных вида исходных данных:

| Исходные данные | Что они предоставляют | Чего они не предоставляют |
| --- | --- | --- |
| Новый проект редактора с `kedra.toml` и пустой `assets/` | Идентичность проекта авторинга и расположение исходников | Приложение Cargo, стартовый код или игру для запуска |
| Обычное приложение Rust с метаданными Cargo | Исполняемый код и явно заданные входы поставки | Автоматическую интеграцию всех возможностей Bevy/Kedra |
| Проверочный пример в репозитории | Узкий пример для проверки контракта | Опубликованный игровой SDK или поддерживаемый шаблон игры |

Создание или открытие проекта редактора не разрешает выполнение кода проекта.
Приложение-хост по-прежнему явно выбирает плагины, загрузку ресурсов, стартовую сцену
и выполнение скриптов. Доступный только для чтения Scene View — не запущенная игра.

Чтобы попробовать инструмент сборки, используйте настроенный пакет `apps/kedra` в репозитории.
Его сборка создаёт редактор, а не игру из открытого проекта. Выполняйте команды этой главы
из корня репозитория и выбирайте новые пути вывода
внутри `target/documentation/examples/build-and-distribution/`.

Примеры используют конфигурацию этого пакета. Сборку, упаковку и запуск всё равно
нужно проверить на вашей машине.

## Порядок работы

1. Изучите приложение, зависимости, build scripts и конфигурацию Cargo; убедитесь в доверии к ним.
2. Установите Rust и необходимые инструменты нативной платформы.
3. Проверьте метаданные Cargo, исходные ассеты, sidecar-файлы, значок и уведомления о лицензиях.
4. Создайте новую проверенную сборку для запуска командой `build`.
5. Используйте `run`, только если намерены запустить только что собранное приложение.
6. Используйте `package`, если нужны также установочные пакеты и переносимые архивы.
7. Перед публикацией проверьте установленное приложение, лицензии и работу на целевой платформе.

Не собирайте недоверенные проекты. Cargo компилирует и выполняет build scripts проекта
и процедурные макросы. Нативная упаковка может скачивать и выполнять вспомогательные
инструменты upstream. Проверка результата не изолирует эти действия в песочнице.

## Значение команд

| Команда | Результат | Запускает приложение? |
| --- | --- | --- |
| `cargo kedra build` | Исполняемый файл, поставка ресурсов, уведомления и `build-result.json` | Нет |
| `cargo kedra run` | Такая же новая сборка, затем явный запрос запуска | Да |
| `cargo kedra package` | Release-сборка, проверенные пакеты/архивы и опись артефактов | Нет |
| `cargo xtask check` | Проверки Rust в репозитории | Нет; это не сборка для распространения |

Без `--release` команды `build` и `run` используют сборку для разработки. Команда `package`
всегда запрашивает release-профиль Cargo. Независимые приложения сохраняют собственную
политику профилей Cargo; инструмент не переносит в них настройки оптимизации редактора.

Каждый каталог вывода должен быть новым. После ошибки могут остаться промежуточные файлы
для диагностики, но это не успешная поставка. Для повтора выберите другой путь;
не используйте повторно и не перезаписывайте прежний результат.

## Приёмка — отдельный этап

Корректный исполняемый файл и соответствующая поставка ресурсов дают полезные структурные
гарантии. Они не доказывают наличие отрисованного кадра, работу ввода, успешное завершение
приложения, корректность установки/удаления или доверие операционной системы.

Настроенные настольные цели: Windows x64 MSVC, Linux x64 GNU, macOS ARM64 и macOS Intel.
Цель должна совпадать с нативным хостом. Эти команды не предоставляют сборку для Web/mobile,
подготовку SDK для другой платформы или сертифицированную матрицу платформ.

Точные опции описаны в [справочнике CLI сборщика](../cli/build-tool.md), а доказательства
за пределами успешной сборки — в [Тестировании](../testing/index.md).
