# Сборка и запуск

Команда `build` собирает приложение без запуска. Используйте `run`, только если намерены
выполнить выбранное приложение. Обе команды компилируют доверенный код проекта;
ни одна из них не заменяет изучение незнакомого проекта Cargo.

## Перед сборкой

Проверьте [конфигурацию приложения](configuration.md), sidecar-файлы исходников и проверенный
`Cargo.lock`. Внутренняя компиляция приложения использует `cargo build --locked` и находит
исполняемый файл по сообщениям об артефактах Cargo, а не угадывает путь внутри target.

Установите rustup и нативный linker: Xcode Command Line Tools в macOS, Visual Studio C++
Build Tools с Windows SDK в Windows или C-компилятор/linker в Linux. В этом checkout
toolchain закреплён в `rust-toolchain.toml`. Для сборки редактора в Linux также нужны
`pkg-config` и библиотеки разработки ALSA/udev, Wayland/X11 и Fontconfig. В Debian/Ubuntu
для Fontconfig нужен `libfontconfig1-dev`; полный [список пакетов](../getting-started/index.md)
приведён в разделе начала работы.

Предварительная проверка ищет Cargo и `codesign`/`plutil` в macOS либо `ldd` в Linux.
Если метаданные содержат `license-config`, также нужен `cargo-about 0.9.2` в PATH.
Проверка не устанавливает недостающие инструменты и не гарантирует наличие всех зависимостей
компилятора/системы. Отдельная явная настройка описана на странице
[подготовки к упаковке](packaging-and-licenses.md).

## Сборка настроенного редактора

Из корня репозитория, после подготовки необходимых инструментов:

```sh
cargo kedra build --package kedra --release --output target/documentation/examples/build-and-distribution/editor-build-01
```

Команда собирает `apps/kedra`, а не игру из проекта редактора. Для каждого повтора
выбирайте новый суффикс или другой новый каталог вывода.

`--manifest-path` выбирает манифест Cargo (по умолчанию `Cargo.toml`). `--package` выбирает
один пакет приложения; без него ровно один пакет workspace должен иметь метаданные
`packager`. `--target` по умолчанию равен triple хоста и должен совпадать с ним.
Без `--release` используется профиль разработки. Произвольная передача Cargo features
или профилей в этих командах сборки/запуска не предусмотрена.

Для build/run `--output` необязателен. Без него инструмент резервирует уникальный каталог
`kedra-build/build-*` внутри target-каталога Cargo и печатает его расположение.
Явный путь вывода отсчитывается от каталога вызова. Ни один вариант не может находиться
внутри исходных ассетов.

## Этапы компоновки

1. Проверить метаданные и наличие нативных инструментов.
2. Зарезервировать новый каталог вывода и подготовить `application/`.
3. Создать варианты значков, обработать исходные ассеты и проверить поставку ресурсов.
4. Скопировать уведомления и, если настроено, собрать лицензии/исходники зависимостей.
5. Скомпилировать выбранную бинарную цель Cargo нативным toolchain.
6. Создать структуру для запуска, проверить архитектуру, ресурсы и уведомления.
7. Записать `build-result.json` как результат успешной сборки.

В macOS создаётся полноценный `.app` с подписью всего bundle, по умолчанию ad-hoc;
DMG для этого не нужен. В Windows/Linux используется исполняемый файл с ресурсами рядом.
Build не выполняет CLI или игровой код приложения, хотя build scripts Cargo и нативные
вспомогательные инструменты остаются выполнением кода в доверенном процессе сборки.

## Читайте результат, не угадывайте путь

`build-result.json` — выходные данные, а не настройки проекта. Версия схемы `1` содержит:

| Поле | Значение |
| --- | --- |
| `application`, `version`, `target` | Выбранное приложение Cargo и нативная цель |
| `application_root` | Каталог для запуска или bundle относительно зарезервированного вывода |
| `executable` | Путь исполняемого файла относительно того же вывода |
| `resources` | Путь проверенной поставки ресурсов относительно того же вывода |

В Windows/Linux корень приложения — `application/`, а `assets/` и `licenses/` расположены
рядом с исполняемым файлом. В macOS корень — `native-application/<productName>.app`,
исполняемый файл находится в `Contents/MacOS/`, ассеты — в `Contents/Resources/assets/`.
Сохраняйте весь корень приложения для запуска, а не только исполняемый файл.

Проверяются формат/архитектура файла, право выполнения там, где оно применимо,
контрольные суммы поставки ресурсов и соответствие уведомлений промежуточной сборке.
В Linux также проверяются отсутствующие динамические библиотеки, в macOS — идентичность
bundle и полная подпись. Это структурные проверки, а не тест рендеринга/ввода.
Одна команда build не создаёт опись установочных пакетов.

## Явный запуск новой сборки

Чтобы собрать редактор и запросить запуск его команды справки:

```sh
cargo kedra run --package kedra --output target/documentation/examples/build-and-distribution/editor-run-01 -- --help
```

Выполняйте команду, только если намерены запустить редактор.
Аргументы приложения идут после `--`; границы аргументов и Unicode сохраняются.
`run` использует только результат текущего вызова, а не прежний каталог сборки.
Передать сохранённый `build-result.json`, чтобы пропустить компиляцию, нельзя.

Рабочий каталог запуска — зарезервированный вывод, а не дерево исходников. Launcher удаляет
унаследованный `KEDRA_ASSETS`, поэтому приложение должно реализовать поиск установленных
ресурсов, а не зависеть от рабочего каталога исходников. Путь к исходникам не подставляется.

В Windows/Linux stdin процесса закрыт, а вывод записывается в `application-stdout.log`
и `application-stderr.log` в каталоге вывода. В macOS Launch Services открывает реальный
`.app` через `/usr/bin/open -n ... --args`; таких же файлов журналов ожидать не следует.
Завершение launcher не предназначено для остановки приложения.

Запуск, рендеринг и ввод для этих примеров команд остаются непроверенными.
«Launch request accepted» означает успешную передачу запроса запуска. Команда не ждёт
завершения приложения, отрисовки кадра или физического ввода. Для этих утверждений нужны
проверки готовности самого приложения и отдельное наблюдение за его окном и вводом.
Команда не добавляет Play.

## Восстановление после ошибок

| Симптом | Действие |
| --- | --- |
| Ошибка выбора приложения/метаданных | Выберите один пакет, проверьте обе таблицы метаданных и единственную бинарную цель. |
| Нет инструмента или неверная версия cargo-about | Явно установите проверенный инструмент; перед повтором проверьте PATH. |
| Вывод существует / находится внутри ассетов | Выберите новый каталог вне исходных ассетов; сохраните прежние свидетельства. |
| Нет sidecar-файлов, неверный SVG или ошибка поставки | Исправьте собственные входные исходники; не заменяйте установленные идентификаторы. |
| Ошибка Cargo или устаревший lockfile | Изучите текущую диагностику; отдельно проверьте изменения зависимостей/lockfile. |
| Неверный исполняемый файл, ресурсы или подпись bundle | Считайте сборку неуспешной; не выдавайте промежуточные файлы за релиз. |
| Ошибка запуска после проверки | Проверенная сборка остаётся на диске; изучите запуск ОС и требования приложения. |

Сохраните точную команду, платформу и диагностику. После исправления причины повторите
с новым выводом. Далее: [упаковка и лицензии](packaging-and-licenses.md).
