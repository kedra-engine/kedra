# Наблюдение и операции

Получение списка методов и наблюдение — операции чтения. Запросы ввода, изменения размера,
захвата и сценариев запускают эффекты, которые могут завершиться на следующих обновлениях
приложения. Разделяйте обмен JSON-RPC и запущенную им операцию.

## Изучите текущее приложение

После [подключения](connecting.md) вызовите `app.describe` и `app.observe` с обычными
ID запросов JSON-RPC. Для наблюдения параметры эффекта не нужны:

```json
{
  "jsonrpc": "2.0",
  "id": "observe-1",
  "method": "app.observe"
}
```

Наблюдение возвращает `session`, `frame`, `windows`, `native`, `cameras`, `screens`,
`elements`, `input_busy` и `truncated`. Записи окон содержат логические/физические
размеры, DPR, фокус и признак основного окна. Записи native сообщают доступное состояние
оконной системы; камеры — свои цели и размеры областей просмотра.

Элемент может сообщать стабильный `id`, runtime `entity`/`parent`, своё `window`, `rect`,
`visible`, `enabled`, `center_unclipped`, `focused`, `text`, редактируемое `value`,
метаданные шрифта и цвета. Это наблюдения настоящего дерева UI, а не отдельная
тестовая компоновка или полное дерево доступности. Текстовые значения и нативные
метаданные могут быть приватными; не публикуйте полные снимки наблюдений.

## Стабильные имена UI и геометрия

Хост размещает `ElementId` и `ScreenId` в настоящем дереве UI. Исходные `ui.id` и
`ui.screen` задают эти идентичности для живых представлений; пассивные проекции их
удаляют. Используйте стабильные имена UI, например `projects.new`, заново наблюдаемые
в целевом окне, а не жёстко заданные временные дескрипторы ECS.

Идентификаторы окон и сущностей в RPC `app.observe` — полноразрядные целые. Сохраняйте их точно:
числовой тип с округлением больших целых может адресовать другое окно или сущность.
Они принадлежат текущему процессу, а не сохранённым идентичностям сцен/узлов. Повторяйте
наблюдение после замены окна, смены проекта, изменения размера или других изменений компоновки.

В диагностике редактора поля области просмотра `eligible_windows` и `pointer_windows`,
а также `host` и `fields` стенда стыковки представлены десятичными строками, включая ответы RPC.
Эти схемы описаны отдельно в справочниках
[редактора](../../api/luau/editor.md) и [тестовых стендов](../../api/luau/testing.md).

`rect` — `[left, top, right, bottom]` в **логических пикселях окна**. Адаптер учитывает
масштаб UI и начало viewport камеры; для ввода не умножайте его на DPR повторно.
Размеры захваченного изображения, напротив, выражены в физических пикселях.

Повтор видимого ID внутри одного окна приводит к ошибке снимка. Список элементов
ограничен 4096 записями и помечается `truncated`, если неполон. Щелчок по ID отклоняет
усечённый снимок, даже если в его начале найдено одно совпадение: уникальность за
пределами этого префикса не установлена.

Щелчок по ID заново находит одну видимую цель в указанном окне, отклоняя выключенные
цели, выключенных предков и обрезанные центры. Эти проверки не доказывают отсутствие
другого виджета поверх центра. Видимость и границы — не полный hit-test и не гарантия
того, что приложение примет действие.

## Два разных ID

| Расположение | Назначение |
| --- | --- |
| Верхнеуровневый JSON-RPC `id` | Сопоставляет этот HTTP-запрос и ответ |
| `params.id` эффекта | Ненулевой UUID одной операции и её аргументов в пределах сеанса |
| `params.session` эффекта | Текущий `app.describe.session` для отклонения старых запросов процесса |
| `params.window` эффекта, где требуется | ID живого окна из текущего наблюдения |

Примеры ниже используют заполнители для сеанса/окна. Перед отправкой подставьте
настоящий сеанс и точный числовой идентификатор окна из наблюдения. UUID — пример ключа
операции, а не зарезервированная идентичность.

Чтобы изменить размер через обычный адаптер ввода, отправьте:

```json
{
  "jsonrpc": "2.0",
  "id": "resize-1",
  "method": "app.resize",
  "params": {
    "session": "SESSION",
    "id": "123e4567-e89b-42d3-a456-426614174001",
    "window": 123,
    "width": 800,
    "height": 600
  }
}
```

При приёме запроса может вернуться `state: "pending"`. Изменение размера ещё не завершено.
Опрашивайте ту же операцию:

```json
{
  "jsonrpc": "2.0",
  "id": "poll-1",
  "method": "app.operation",
  "params": {"id": "123e4567-e89b-42d3-a456-426614174001"}
}
```

Полные квитанции содержат `id`, `request_hash`, `state` и `detail`. Состояния: `pending`,
`succeeded` и `failed`. Результат зависит от операции: доставка ввода/resize возвращает
`{"delivered":true}`, а завершение захвата сообщает опубликованный артефакт кадра.
После доставки запросите наблюдение ещё раз и проверьте, произошло ли нужное изменение.

## Правила повторов и ошибок

Для совпадающего повтора сохраняйте ID операции и аргументы. Повторное использование
этого ID с другими аргументами отклоняется. Завершённые результаты терминальны; позднее
завершение не может их заменить. Предпочитайте запрос квитанции повтору неопределённого
эффекта.

Коллекция хранит не более 256 квитанций. Завершённые вытесняются от старых к новым;
активные не вытесняются. `Unknown or expired operation` — явная ошибка, а не успешное
пустое действие. После вытеснения квитанции долговечной защиты от повторов нет.
Поручите внешнему супервизору отслеживать операции и сроки: это не журнал транзакций.

Валидация может отклонить запрос до допуска; другие ошибки попадают в квитанцию
допущенной операции. Проверяйте и JSON-RPC `error`, и `state`/`detail` квитанции.
Таймаут транспорта возможен после постановки в очередь: это не откат, а новый UUID
может повторить эффекты.

[Тестирование](../testing/index.md) объясняет, что проверяют наблюдение состояния,
доставка событий, считывание кадров, сравнение пикселей и настоящий ввод ОС.

Лимиты транспорта и уровни ошибок описаны в
[Программах и диагностике](programs-and-diagnostics.md). Правила наблюдения и хранения
квитанций в пределах одного процесса реализованы в [исходнике наблюдения][observe]
и [исходнике квитанций][operations] (English).
