# Проверки репозитория и запуск тестов

`cargo xtask` — инструмент разработки репозитория, а не команда сборки открытого
авторского проекта. Псевдоним собирает оркестратор в `target/xtask-bootstrap`;
перед выполнением оркестратор меняет рабочий каталог на корень репозитория Kedra.

Процесс разработки и ревью описан в [Тестах и ревью](../../contributing/tests-and-review.md).
Авторам приложений и сценариев для проверки собственного приложения нужна
[тестовая цель локального сборщика проекта](build-tool.md).

## Задачи репозитория

```sh
cargo xtask check --non-interactive
cargo xtask features --non-interactive
```

| Задача | Что выполняется |
| --- | --- |
| `files` | Ограничения роста файлов, включая отслеживаемые файлы, попавшие под правила игнорирования |
| `architecture` | Слои зависимостей workspace, лицензии и наследование lint |
| `fmt` | `cargo fmt --all -- --check`; не применяет форматирование |
| `lint` | Clippy с фиксированными зависимостями для workspace, всех целей и Cargo features; unsafe запрещён, предупреждения считаются ошибками |
| `test` | Тесты workspace с фиксированными зависимостями для всех целей и Cargo features, затем отдельные doctests |
| `doc` | Документация API workspace со всеми Cargo features и фиксированными зависимостями, без документации зависимостей; строгая проверка предупреждений и ссылок rustdoc |
| `check` | `files`, `architecture`, `fmt`, `lint`, `test`, `doc` по порядку |
| `features` | Workspace с Cargo features по умолчанию и без них; отдельные проверки крейтов runtime/данных и отсутствия диагностики в release |
| `visual` | Явная локальная проверка эталона или сравнение снимков |

У `check` семь этапов: `test` содержит два вызова Cargo. Задача не включает
`features`, нативные сценарии рабочего стола или локальное сравнение изображений. `doc`
генерирует локальную документацию Rust API, а не установленный или опубликованный справочник.

`features` проверяет все цели workspace с default и без default features, затем
изолированные библиотеки без default features: `kedra_app`, `kedra_script`,
`kedra_scene`, `kedra_assets` и `kedra_ui`. В конце выполняет `launch::tests` в
`kedra_app` под профилем `release-boundary` без default features. Это не сертификация
всех сочетаний target/features или нативного взаимодействия.

Если задача не указана в интерактивном терминале, открывается клавиатурное меню.
Вне этого режима отсутствие задачи вызывает ошибку, а не запрос или выбор `check`.
Наличие `CI`, перенаправленные потоки, `TERM=dumb` или `--non-interactive` отключают
интерактивный UI. Явно указанная задача не требует меню.

Обычные запуски задач транслируют вывод процессов и записывают отдельные текстовые
логи в `target/xtask/logs`. Ошибка этапа останавливает последующие; сводка показывает
пропущенную работу. Ранняя ошибка компиляции может возникнуть до создания лога.
Логи не отправляются и не очищаются автоматически; перед передачей проверьте пути
и чувствительные данные. Принудительное завершение может помешать итоговой сводке.

## Передача аргументов нативным сценариям

```sh
cargo xtask test -- features --only hierarchy --output target/cli-hierarchy
cargo xtask test -- components --output target/cli-components
```

Только `test` принимает завершающие аргументы сценария. Без аргументов после `--`
выполняются Rust-тесты/doctests. С аргументами вместо них собирается и выполняется
обычная цель `tools/test` через `kedra_test`; Rust-набор дополнительно не запускается.
Нативные опции ставьте после разделителя. Visual-опции перед ним отклоняются при
выбранном нативном маршруте.

Все команды сценариев принимают необязательный `--output PATH`. Явный каталог
должен быть новым; относительные выходы отсчитываются от репозитория. Без опции
средство запуска резервирует каталог в `target/test/ui-runs` с префиксом `rust-`. Нужны
свободный рабочий стол поддерживаемой платформы и её зависимости. Нативные запуски
собирают доверенный код, запускают приложения и могут внедрять ввод. Не запускайте
их только ради проверки синтаксиса.

### Текущие аргументы сценариев

- `features [--only NAMES]`: имена поведенческих сценариев через запятую. Сейчас
  доступны `startup`, `luau`, `browser`, `hierarchy`, `inspector`, `workspace`,
  `window-chrome`, `docking`, `docking-states`, `scene-view`, `scene-navigation`,
  `inspector-fixture` и `dock-fixture`. Неизвестные/повторные имена отклоняются.
  Выбранное подмножество не является приёмкой полного набора.
- `components [--source PATH] [--policy PATH] [--only NAMES]`: 22 случая кнопок/полей
  в двух сеансах. По умолчанию — `docs/ui/corpus/text` и
  `docs/ui/corpus/text-policy.json`, относительно репозитория. `--only` выбирает
  допустимые ID случаев для диагностики, не имена сценариев функций приложения и не полную приёмку.
  Изменённый граф зависимостей всё равно требует ревью и одобрения файла блокировки;
  подмножество не обходит это ограничение.
- `native-switch` и `native-projection`: каждой нужны `--manifest-path PATH`,
  `--assets PATH` и `--project-assets PATH`. Это конкретные контракты для полной
  частной копии канонического тестового проекта, а не запуск любых игр.
- `export`: обязательна ровно одна из опций `--text-plugin` или `--text-bundle PATH`.
  Записывает локальный плагин Figma или импортирует загруженный архив исходников.
  Это явный экспорт/импорт источников, не нативная приёмка и не автопубликация.

Сценарии функций проверяют поведение и синхронизацию рендерера, а не совпадение пикселей.
Корпус компонентов сравнивает с независимыми эталонами только перечисленные элементы,
а не все панели редактора. Требования к готовности, изоляции исходников и проверке отчётов
описаны в руководствах ниже. Ни один маршрут не разрешает обновлять эталоны без ревью.

## Offline-задача visual

```sh
cargo xtask visual --config PATH/TO/comparison.json \
  --actual PATH/TO/evidence.json --output target/cli-comparison
cargo xtask visual --inspect-reference PATH/TO/manifest.json \
  --output target/cli-reference
```

Сравнение требует `--config`, `--actual` и `--output`. Проверка эталона требует
`--inspect-reference` и `--output`; она несовместима с `--config` и `--actual`.
Выход — новый каталог артефактов. Эти флаги допустимы только для `visual`;
завершающие нативные аргументы у этой задачи не принимаются.

Этот маршрут читает готовые файлы и не снимает работающий экземпляр приложения.
Целостность эталона не означает нативную приёмку; успешное сравнение не является
независимым одобрением дизайна. Не заменяйте не прошедший эталон фактическим
изображением ради успешной проверки.
