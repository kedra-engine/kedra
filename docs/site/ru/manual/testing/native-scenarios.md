# Нативные сценарии

[Справочник проекции тестового стенда](../../api/luau/testing.md#projection-api-только-этого-стенда)
описывает явно допущенные диагностические вызовы.
[Справочник игровых скриптов](../../api/luau/game-host.md) отдельно описывает разрешение
переключателя; ни один из них не является универсальным игровым SDK.

Нативные сценарии проверяют обычные приложения с настоящими окнами и кадрами рендерера.
Это явные локальные операции, а не автоматическое следствие Rust-тестов.

## Перед разрешением запуска

Выбор команды описан в [запуске тестов](../cli/repository-and-tests.md), а границы сервиса —
в [контрактах ввода и захвата](../automation/input-and-captures.md).

1. Доверяйте проекту и его Cargo-конфигурации: компиляция может выполнять build-код.
2. Установите [нативные зависимости](../getting-started/index.md), включая графическую поддержку.
3. Используйте свободный разблокированный рабочий стол для окон, смены фокуса и внедрения ввода.
4. Выберите новую выходную директорию. Не перезаписывайте прошлый запуск, скрывая ошибку.
5. Не допускайте изменения канонического проекта и личных настроек редактора.
6. Для потенциально блокирующих собственных проверок ограничьте время работы процесса извне.

Предварительная проверка подтверждает разблокированную консоль в macOS. Linux требует
`DISPLAY`, X11 и оконный менеджер. Feature-runner редактора удаляет `WAYLAND_DISPLAY`
из окружения дочерних процессов, выбирая этот backend даже при входе через Wayland.
Это не приёмка Wayland или облачных машин. Программный resize в native Wayland может
сохранить прежний физический размер при изменении тестового DPR; набор не подтверждает
эту границу. Квитанция доставки resize не гарантирует применение размера композитором.
В Windows разблокировка так не проверяется: подготовьте рабочий стол самостоятельно.
Успешная подготовка не означает, что нужное взаимодействие прошло успешно.

## Выберите feature-процесс

Из корня репозитория явно запустите выбранные сценарии функций или весь набор:

```sh
cargo xtask test -- features --only hierarchy --output target/test/hierarchy
cargo xtask test -- features --only scene-navigation --output target/test/navigation
cargo xtask test -- features --only luau --output target/test/luau
cargo xtask test -- features --output target/test/features
```

Каждому вызову нужен свежий путь. Без `--output` драйвер создаёт новый запуск в
`target/test/ui-runs/`. Неизвестные и повторные имена вызывают ошибку, а не исчезают из набора.
`--only` принимает точные имена через запятую; выборка не означает приёмку полного набора.

| Задача | Существующая выборка | Что ожидать |
| --- | --- | --- |
| Project manager и формы | `startup`, `luau` | Изолированный старт; Luau проверяет программу формы редактора |
| Навигация источников | `browser`, `hierarchy`, `inspector` | Приватная копия проекта и проверки состояния |
| Workspace/chrome | `workspace`, `window-chrome` | Окна, компоновка, фокус и жизненный цикл |
| Docking | `docking`, `docking-states`, `dock-fixture` | Обычная обработка жестов, состояние и синхронизация рендерера |
| Preview/навигация | `scene-view`, `scene-navigation` | Готовность ресурсов/компоновки и ограниченное взаимодействие |
| Трансформации исходников | `scene-transform` | Move/Rotate/Scale, Undo/Redo/Save, отключение инструментов рукой, MMB и колесо в главном/плавающем виде |
| Изолированный Inspector | `inspector-fixture` | Явная авторская сцена без старта проекта |

Hierarchy включает фазы поведения и удобства взаимодействия в одном сеансе с отдельными результатами
и квитанциями кадров. Команды `hierarchy-appearance` и screenshot-эталона Hierarchy нет.
`scene-navigation` использует модель и смешанную сцену для навигации. Он не заменяет проверки
PNG, моделей, UI, смешанного предпросмотра и переноса между окнами в `scene-view`.
`scene-transform` проверяет внедрённый MMB. Физический MMB и полёт с RMB требуют
отдельной приёмки; внедрённые события не подтверждают аппаратный ввод.

## Ответственность драйвера

Драйвер собирает обычный debug-редактор и создаёт/проверяет поставки ресурсов редактора и проекта.
Проектные случаи получают полные копии `tests/fixtures/test_project` с сохранёнными идентичностями.
Байты копий проверяются; в конце набора повторно сверяется список канонических исходников.
Create в startup — явная проверяемая операция продукта, а не генерация фикстуры.

Состояние и настройки сценария остаются в `private/<scenario>/`; поддержка отклоняет личные пути
настроек. Docking перезапускается с сохранённым состоянием этого сценария
для проверки восстановления.
Изолированная docking-сцена выполняется дважды без проектных панелей/старта/настроек.
Явные сцены используют обычный редактор и общий `--scene`, а не альтернативные app-цели.

Общие API `kedra_test` находят исполняемые файлы Cargo, управляют процессами и соединениями,
проверяют результаты захвата. Rust-функции проекта определяют готовность приложения,
проверяют его поведение и разрешают завершение. Проверяемое runtime-приложение не зависит
от `kedra_test` и не принимает произвольный код для удалённого выполнения. Внешний Rust-сценарий
использует этот крейт для управления приложением и проверки результатов.

## Готовность и deadlines

Супервизор ждёт заданных условий состояния, допущенных ресурсов и наблюдаемой компоновки,
а не просто делает паузу в ожидании правдоподобного снимка. Файл учётных данных означает лишь
готовность транспорта, а не загрузку документа, создание элемента UI или готовность предпросмотра.

| Механизм | Реализованная граница |
| --- | --- |
| Публикация учётных данных | 45 секунд с проверкой раннего завершения процесса |
| Один HTTP-запрос | Общий таймаут 8 секунд; без перенаправлений и прокси |
| Квитанция нативной операции | Срок опроса 12 секунд |
| Явная активация окна | Восемь секунд на подтверждение, без подмены состояния или повторов ввода |
| Нативный readback | Восемь реальных секунд независимо от FPS; поздняя публикация запрещена |
| Создание/восстановление floating host | Десять реальных секунд; deadline проверяется до публикации |
| Бюджет конечной Sequence по умолчанию | 45 секунд на всю программу, не на каждый помощник |
| Именованная последовательность Luau в приложении | Внешний срок опроса 55 секунд |
| Обычная готовность состояния/узла редактора | Срок опроса 40 секунд |
| Разрешённое штатное завершение | Успешный выход процесса за 10 секунд |

Сроки опроса проверяются между попытками; ограниченный по времени RPC или предикат может
увеличить общее время. Это не единый жёсткий срок для компиляции или всего набора.
Собственный бюджет последовательности тоже действует; сроки помощников не прибавляются
к нему. Luau проверяет deadline до и после предиката, но не прерывает нативный вызов.
Наблюдение dock-preview ждёт живого жеста и штатной готовности кандидата, затем renderer fence.
Повторные пиксельно одинаковые readback не требуются; отменённый жест не воспроизводится заново.
Потенциально блокирующим собственным тестам нужен отдельный процесс, который можно завершить
по внешнему таймеру. При Drop незавершённые дочерние процессы принудительно завершаются,
а их статус собирается. Такая очистка не считается успешным штатным выходом.

Эффекты отправляются один раз, затем опрашиваются существующие квитанции. Таймаут не откатывает
эффект. Не повторяйте неопределённую операцию вслепую и не переключайте механизм незаметно.
Отсутствующая/ошибочная программа приложения проваливает сценарий; клиент не внедряет Luau-исходник.

## Ввод внедрённый, не физический

`Client::input`, `resize` и `capture` выполняют зарегистрированные конечные программы в приложении.
Ввод проходит через нативную обработку Bevy, но это не физическая мышь и не щелчок по кнопке ОС.
Внедрённый `close_window` проверяет обработку запроса закрытия, а не кнопку операционной системы.
Операции с моделью проекции в независимой игре не заменяют проверки жестов редактора.

Для физической приёмки отдельно зарезервируйте машину и используйте настоящий указатель и
клавиатуру: перетаскивайте вкладки, отпускайте/отменяйте жест, двигайте/меняйте размер окон,
закрывайте нативными кнопками и проверяйте фокус/состояние в реальных кадрах. При необходимости
проверьте IME, диалоги выбора файлов и переходы между мониторами с разным DPI
на заявленной платформе.
Отдельно запишите оборудование, путь ввода и наблюдаемый результат.
Успех внедрённого сценария не означает выполнения этих физических действий.

## Независимые runtime-потребители

`native-switch` и `native-projection` требуют конкретный package/bin `kedra-test-project`,
полную приватную копию канонического проекта и две независимо проверенные поставки ресурсов.
Они не запускают произвольный манифест. Копии сохраняют относительную структуру зависимостей;
генерировать файл блокировки разрешено только в копии, не в канонических исходниках.

При готовой копии в `target/native-switch/project`, проверенных поставках по указанным путям
и новом пути результата конкретный вызов выглядит так:

```sh
CARGO_TARGET_DIR="$PWD/target" cargo xtask test -- native-switch \
  --manifest-path "$PWD/target/native-switch/project/Cargo.toml" \
  --assets "$PWD/target/test/editor-delivery" \
  --project-assets "$PWD/target/native-switch/game-delivery" \
  --output "$PWD/target/native-switch/result"
```

Оба независимых сценария сначала проверяют готовность проекции игры, исключённой из workspace,
затем собирают и запускают два процесса и требуют успешного выхода через нативный запрос закрытия.
Проверки корневого workspace не запускают этот проект. Другим приложениям нужен свой Rust-тест;
`cargo kedra test` выбирает такую проектную Cargo-цель, а не предоставляет готовый сценарий.

Подготовка полной копии, файла блокировки и обеих поставок описана в канонической
[инструкции для нативной игры][native-game-recipe].
После подготовки проверьте этот хост отдельно в режиме **headless**:

```sh
CARGO_TARGET_DIR="$PWD/target" cargo test --locked \
  --manifest-path target/native-switch/project/Cargo.toml \
  --bin kedra-test-project docking::scripting::tests
```

Запускайте из корня репозитория. Команда проверяет три контракта готовности проекции хоста,
а не ввод и кадры нативного приложения; записывайте её результат отдельно. `native-projection`
принимает те же аргументы, что `native-switch`, но проверяет независимую композицию стыковки
в двух процессах, а не запуск переключателя.

## Готовность нативных задач

В Linux Rust-supervisor отдельно проверяет общий readiness adapter без смены
частоты кадров редактора, RPC polling и активной Luau-последовательности:

```sh
cargo xtask test -- native-wakeup --output target/test/native-wakeup
```

Команда собирает конкретный example `kedra_wakeup/native_readiness`, подтверждает
сон по OS wait state собственного процесса и освобождает worker через stdin.
Владелец не опрашивает handle до освобождения worker: readiness должна
регистрироваться автоматически при создании, а не случайным кадром.
Успех и отказ worker требуют GPU-readback и чистого завершения; отказ сохраняет
предыдущий clear-color кадр. Контроль без wakeup должен оставить результат worker
непринятым до deadline и принудительной очистки. Ввод в окно для разблокировки
не отправляется. Одноцветные кадры — диагностика состояния, не component references.
Supervisor также проверяет deadline 350 ms через тот же ReactivePlugin с
диагностическим бесконечным idle: без worker release, RPC, Luau или ввода в окно.
Это не приёмка физической задержки ввода, других платформ или бесконечного сна
редактора. Сам редактор сохраняет safety sweep 100 ms и active demand подсистем;
см. [ADR 0045][reactive-policy].

[reactive-policy]: https://github.com/kedra-engine/kedra/blob/main/docs/decisions/0045-bounded-reactive-editor.md
Результат — `public/report.json`; логи и readbacks остаются в `private/`.

## Диагностика без потери доказательств

Для feature/component/game сценариев откройте `public/index.html` и `public/report.json`.
Readiness-сценарий публикует `public/report.json`. Ошибки подготовки, невыполненные выборки
и сбои случаев обозначаются явно. Сценарии функций проверяют поведение: временные проверенные
PNG удаляются, остаются квитанции рендерера и размеры, а не сравнения пикселей и галереи снимков.
Перед новым запуском локально изучите `private/`, включая `native.log` и `rpc-errors.jsonl`.
При `KEDRA_DOCK_TRACE=1` сценарии редактора также сохраняют ограниченный `input-trace.json`
в приватном каталоге сессии: ввод, фокус, размеры viewport и изменения масштаба.
Не публикуйте учётные данные, полные RPC-данные, приватные копии проектов или личные пути.

Потеря фокуса отменяет docking-жесты; не восстанавливайте их незаметно ради зелёного результата.
Честно укажите прерывание и ограничения платформы. Переходите к
[Визуальной проверке](visual-verification.md) только для отдельно принятой области компонентов.
