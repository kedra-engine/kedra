# Проверки репозитория

Во время разработки запускайте узкие тесты, затем общую проверку и тесты в нужных средах.
Эти команды проверяют Rust-код репозитория, но не запускают нативную приёмку.
В частности, `cargo xtask features` и `cargo xtask test -- features` — разные задачи.

## Подготовьте машину

Синтаксис запуска описан в [справочнике CLI репозитория](../cli/repository-and-tests.md).
Для выбора между сборкой и тестами используйте [карту задач CLI](../cli/index.md).

Установите Git, rustup, нативный компоновщик и пакеты разработки из раздела
[Начало работы](../getting-started/index.md). Репозиторий выбирает `rust-toolchain.toml`.
Первой загрузке зависимостей нужен доступ в сеть. Обычные проверки используют lockfile.
Не убирайте `--locked` ради обхода расхождения зависимостей.

Базовому Rust-циклу не нужны приватный сервис, учётные данные, Python или подписка на ИИ.
Headless-проверкам не нужен GPU, но компиляции нативных зависимостей нужны пакеты платформы.
Инструменты Markdown, ссылок, безопасности и покрытия устанавливаются отдельно.

## Начните с контракта владельца

Запустите узкий набор тестов для изменяемого кода, например:

```sh
cargo test -p kedra_docking --test contracts --locked
cargo test -p kedra_editor --test contracts --locked styles::
cargo test -p kedra_editor --lib --locked workspace::
```

Первая проверяет публичные контракты топологии, идентичности, кандидатов и снимков
без нативного окна.
Вторая выбирает контракты стилей редактора, но не сравнивает отрисованный текст.
Третья выбирает приватные workspace-тесты; заданная геометрия не доказывает нативную компоновку.
Cargo-фильтры выбирают по подстроке. Проверяйте список, включая результаты с нулём тестов.
Успешная команда, ничего не выбравшая, не проверяет нужный контракт.

## Запустите Rust gate

```sh
cargo xtask check
```

Задача выполняет восемь этапов по порядку и останавливается после первого сбоя:

| Этап | Что проверяется |
| --- | --- |
| File growth policy | Список Git, включая отслеживаемые ignored-файлы; 1000 строк / 64 KiB |
| Dependency architecture | Слои workspace-зависимостей, лицензии пакетов и наследование lint |
| Dependency exception policy | Согласованные advisory, срок пересмотра, ограничения callers и точные исключения дубликатов |
| Rust formatting | `cargo fmt --all -- --check`; без записи форматирования |
| Clippy | Workspace, все цели и Cargo features, locked; запрет unsafe и предупреждений |
| Unit and integration tests | Workspace, все цели и Cargo features, locked |
| Documentation tests | Отдельный запуск workspace doctests со всеми Cargo features, locked |
| API documentation | Workspace rustdoc без зависимостей, все Cargo features; запрет предупреждений |

All-target tests не запускают обычные бинарные нативные сценарии как приложения.
`check` не включает feature-матрицу, сравнение изображений, внешние сканеры и сборку сайта.
Это не оптимизированный release редактора и не приёмка сборки/упаковки/установки.

Для узкого повтора используйте `cargo xtask files`, `architecture`, `dependency-policy`,
`fmt`, `lint`, `test` или `doc`.
Без хвостовых аргументов `cargo xtask test` запускает Rust-тесты, затем doctests.
Аргументы после `--` передаются нативному test-tool, а не служат фильтрами Rust-тестов.

## Проверьте feature-конфигурации независимо

```sh
cargo xtask features --non-interactive
```

Команда проверяет workspace с Cargo features по умолчанию и без них, затем отдельно минимальные
библиотеки `kedra_app`, `kedra_script`, `kedra_scene`, `kedra_assets`, `kedra_ui` и `kedra_wakeup`,
а также тесты `kedra_profiling` без профилирования.
Раздельные вызовы не позволяют объединению Cargo features редактора незаметно добавить возможности.
Одна сборка со всеми Cargo features не подтверждает работу минимального потребителя.

Последний этап запускает тесты запуска `kedra_app` в профиле `release-boundary` с отключёнными
debug assertions. Они проверяют отсутствие диагностических CLI и транспорта в поставляемом
приложении. Профиль использует оптимизацию для разработки, а не release-оптимизацию редактора.
Каждый подпроцесс должен завершиться успешно; ошибка останавливает задачу.

## Читайте прогресс и исправляйте сбои

Явные задачи печатают этапы, передают диагностику дочерних процессов и дают итог по этапам.
Журналы Rust-задач находятся в `target/xtask/logs/`; путь текущего запуска выводится на экран.
Пропущенные этапы не считаются успешными. Ошибка bootstrap-компиляции возможна до создания лога.
Принудительное завершение может оставить неполный журнал без итоговой сводки.

CI, перенаправление потоков и `--non-interactive` отключают меню и анимацию, но не диагностику.
Без задачи вне интерактивного терминала будет ошибка. Выбирайте через `cargo xtask --help`.
Оркестратор собирается в `target/xtask-bootstrap/`; дочерние проверки используют обычную
Cargo-директорию, в том числе `CARGO_TARGET_DIR`, если она задана.

Исправьте сбой в отвечающем за него модуле, затем повторите узкий этап и обязательную проверку.
Применяйте `cargo fmt --all` осознанно, не перезаписывая чужие изменения.
При ошибке архитектуры исправьте распределение обязанностей, не добавляйте крейт-переадресатор.
При превышении размера разделяйте ответственность, не добавляйте исключения и не сжимайте текст.
Не отключайте тесты, не ослабляйте lint/security и не меняйте эталон ради зелёного результата.

## Дополнительные доказательства — отдельно

Проверка Markdown, локальных ссылок, зависимостей, безопасности и пар страниц сайта —
отдельные проверки репозитория, а не скрытые этапы общей проверки Rust.
Когда они нужны для изменения, их результат фиксируется отдельно.

Покрытие информационное, без минимального процента. Свежее измерение всё равно должно
завершиться успешно и создать непустой отчёт. Нужны cargo-llvm-cov 0.7.1 и `llvm-tools-preview`:

```sh
cargo llvm-cov --workspace --all-targets --all-features --locked \
  --lcov --output-path target/coverage.lcov
```

Команда выполняет headless workspace-тесты, не нативные сценарии приёмки.
Наличие исходников драйвера в знаменателе не означает выполнения его процессов.
Не добавляйте искусственные тесты, исключения или нативные запуски ради процента.
См. [Нативные сценарии](native-scenarios.md) для интеграции и
[Визуальная проверка](visual-verification.md) для принятой области screenshot-проверок.

## Внешние инструменты и безопасность

Эти отдельные команды выполняются из корня репозитория. Установка и обновление базы
уязвимостей требуют сети; ничто ниже не включено неявно в общую проверку Rust.
[Контракт тестирования](../../contributing/contracts/testing.md#инженерные-инструменты-и-pins)
задаёт версии инструментов, область проверок и исключения. Изучите команды до разрешения установки.

```sh
# Install pinned tools explicitly; these commands fetch/build external source.
cargo install rumdl --version 0.3.0 --locked
cargo install cargo-deny --version 0.19.0 --locked
cargo install lychee --version 0.24.2 --locked
rustup component add llvm-tools-preview
cargo install cargo-llvm-cov --version 0.7.1 --locked
# With Go 1.24+ installed separately:
go install github.com/zricethezav/gitleaks/v8@v8.24.2
```

Добавьте исполняемые файлы из `go env GOPATH`/bin в PATH до сканирования. Форматируйте осознанно:
`rumdl fmt .` меняет Markdown, `rumdl check .` — нет. Команда проверки ссылок проверяет
локальные фрагменты, не обращаясь к внешним сайтам:

```sh
rumdl check .
cargo deny --locked check
lychee --offline --include-fragments --no-progress --root-dir "$PWD/docs/site" './*.md' docs
cargo test -p xtask --test portable_contracts --locked
cargo test -p kedra_editor --test contracts --locked icons::
python3 -m unittest discover -s tools/ci -p 'test*.py'
python3 -m unittest discover -s tools/distribution -p 'test*.py'
```

Две команды поиска Python-тестов проверяют инструменты CI и распространения (CI использует
Python 3.13); нативным тестам они не нужны. Проверки переносимости и значков проверяют политику
и метаданные, а не пиксели. Покрытие измеряется отдельной командой выше. Проверка сайта описана
в [руководстве по документации](../../contributing/documentation.md).

Сканирование рабочего дерева запускайте из корня **чистого checkout или чистой копии
исходников по списку Git**, включающей `.gitleaks.toml`:

```sh
gitleaks dir . --redact --exit-code 1
```

Это не сканирование истории. Игнорируемые результаты сборки тоже проверяются и могут содержать
криптографические примеры зависимостей; используйте чистую копию исходников,
не ослабляйте детекторы. CI отдельно
использует полную историю (`fetch-depth: 0`) и `gitleaks git --redact --no-banner .`.
[Политика ID](../../contributing/contracts/testing.md#проверенные-несекретные-figma-identities)
не разрешает исключения для учётных данных.

С Python 3.11+ и закреплённой версией Gitleaks в PATH явно запустите локальную проверку политики:

```sh
python3 tools/security/check_gitleaks.py --gitleaks gitleaks
```

`--gitleaks /path/to/gitleaks` выбирает установленный сканер. Отсутствие или неверная версия —
ошибка, а не пропуск. Реальный сканер проверяет конфигурацию, происхождение и синтетические
примеры запрещённых данных; результаты со скрытыми секретами попадают в новый
`target/gitleaks-policy-*`. Сеть и аккаунт не нужны; команда не входит в обычный поиск
Python/Rust-тестов. Проверьте артефакты перед передачей.
