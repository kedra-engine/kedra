# Компоненты Rust и интеграция приложения-хоста

[Руководство Rust API](../../api/index.md) объясняет, как сгенерировать точный справочник.
По ссылкам на исходники и контракты ниже доступен полный контекст примера компонента.

Используйте обычный код Bevy для игровой логики. Чтобы тип был доступен в исходных документах,
Inspector или скриптах, явно подключите каждую интеграцию в приложении-хосте на Rust.
Kedra не обнаруживает класс и не превращает его автоматически в компонент, инспектор,
схему исходников и скриптовый API.

## Типы runtime — не схемы авторинга

Нативные системы могут использовать `Component` Bevy, не сохраняя его в исходниках Kedra.
Одной регистрации отражения тоже недостаточно: `ComponentPolicies` добавляет к реестру
типов Bevy явный ключ исходных данных, точную версию схемы и валидатор.
Это список допуска поверх отражения Bevy, а не вторая система отражения.

Сериализованная сторона этой регистрации описана в разделе
[полей документа и карт компонентов](../scenes/index.md#поля-документа).

Следующий **фрагмент**, адаптированный из компонента `Tuning` и `setup` независимого
runtime-теста, показывает границу регистрации. `app` — инициализированное приложение
Bevy; `policies` необходимо передать компиляции исходников или службе приложения-хоста.

```rust
use bevy::prelude::*;
use kedra_scene::reflection::ComponentPolicies;

#[derive(Component, Clone, Reflect, Debug, PartialEq)]
#[reflect(Component)]
struct Tuning {
    speed: f32,
    health: u32,
}

// Excerpt from a fallible host setup function.
app.init_resource::<AppTypeRegistry>();
let registry = app.world().resource::<AppTypeRegistry>().clone();
let mut policies = ComponentPolicies::default();
policies.register::<Tuning>(&mut registry.write(), "game.tuning", 1, |value| {
    let tuning = Tuning::from_reflect(value)
        .ok_or_else(|| kedra_scene::Error("invalid tuning".into()))?;
    if !tuning.speed.is_finite() || tuning.speed < 0. {
        return Err(kedra_scene::Error(
            "speed must be finite and nonnegative".into(),
        ));
    }
    Ok(())
})?;
```

Соответствующие исходные данные — `ComponentData::ron(1, "(speed:1.0,health:10)")`
под ключом `game.tuning`. Это типизированные данные компонента, не скрипт и не запрос
на выполнение кода. Runtime-тест меняет `speed` варианта на `3.0`, создаёт два экземпляра
и проверяет, что изменение `health` одного живого экземпляра не меняет второй.
Изменения живого состояния также не затрагивают неизменяемый скомпилированный снимок исходников.

### Правила допуска

- Неизвестные ключи и несовпадающие версии приводят к ошибке: runtime не пропускает
  неизвестные данные и не устанавливает совместимые читатели. Нужна миграция схемы.
- Авторируемый тип должен отражать `Component` и поддерживать создание через отражение.
- Хуки вставки и жизненного цикла запрещены. Обязательные компоненты требуют собственных
  политик без побочных эффектов, кроме явно разрешённых типов представления движка.
- Валидаторы не должны иметь побочных эффектов. Игровую логику активируют после
  `PrefabReady`, а не в хуке, способном сработать при изолированной проверке исходников.
- Сохраняемые поля `Entity` требуют сопоставления Bevy через `#[entities]`. Компиляция
  проверяет, что оно обходит все сериализованные ссылки; одного отражения поля недостаточно.

Ссылки исходников остаются символическими: локальные адреса узлов с областью экземпляра
и внешние порты преобразуются в runtime-сущности при материализации. Ссылки на ассеты
сохраняйте как нативные пути ассетов. Постоянные идентичности документов, узлов и экземпляров
остаются UUID; runtime-дескрипторы `Entity` их не заменяют и не подходят для сохранения.

Регистрация политики не обещает визуальное редактирование, специальное представление
Inspector, поддержку рендеринга или привязку Luau. Текущий Inspector редактора работает
только для чтения и имеет собственный набор представлений. Эти интеграции оценивают отдельно.

## Компиляция исходников и живые системы

`CompiledPrefab::compile` работает в изолированном World. Он проверяет композицию,
версии компонентов, переопределения полей, валидаторы, символические ссылки и нативные
зависимости до создания живого экземпляра. Скомпилированный снимок исходников неизменяем.
Публикация исходников создаёт новую ревизию, а не незаметно обновляет существующие экземпляры.

`PrefabInstance` хранит точную компиляцию и отображение адресов исходников в принадлежащие
ему живые сущности. Два экземпляра разделяют смысл исходников, но не идентичности сущностей.
`PrefabReady` означает полностью успешное создание экземпляра, а не готовый кадр GPU.
Выбранная приложением-хостом гидратация может предъявлять дополнительные требования готовности.

Нативные системы обычным образом работают с этими живыми компонентами Bevy. Инициализацию,
которой нужен полный префаб, размещайте после границы его готовности. Для скриптов
упорядочивайте предметные системы относительно `ScriptSystems::Update`,
`ScriptSystems::FixedUpdate` и `ScriptSystems::Run`, не предполагая порядок экземпляров скриптов.

Изменения живого состояния — игровые эффекты. Они не создают переопределения исходников,
не помечают документ изменённым и не реализуют Save. Для сохранения авторского изменения
используйте проверяемые транзакции исходников и
[протокол Save под управлением источников](../scenes/source-editing.md).

## Полные логические пути в нативном коде

Нативный код приложения-хоста обращается к сценам и префабам по полным логическим путям,
например `game://Native/switch.scene.ron` и `application://catalogs/native.prefabs.ron`
из тестового приложения. Это не абсолютные пути файловой системы. Разрешайте их через
загруженный каталог источников, проверяйте принадлежность и используйте опубликованную
ревизию; не создавайте вторую таблицу поиска UUID и не фиксируйте UUID/числовой ID
документа в игровом коде.

Это правило не переписывает сериализованные ссылки: UUID документов, узлов и экземпляров
и сведения о происхождении источников сохраняются. Подробнее о связи пути с каталогом
и явном владении монтированием — в [жизненном цикле сцен](../scenes/lifecycle.md).

## Если компонент не загружается

Сначала проверьте ключ и версию в исходнике, затем регистрацию политики, создание через
отражение и политики обязательных компонентов. Проверяйте валидатор после переопределений:
корректная база не делает отрицательное или неконечное значение скорости допустимым
после переопределения. Для ссылок
на сущности проверяйте привязки портов, область узла и `#[entities]`, а не равенство числовых ID.

Отклонённая компиляция не должна менять живой экземпляр. Контрактные тесты сцен покрывают
ошибочные данные и ссылки, а также независимое владение экземплярами; успешный нативный
рендеринг проверяют отдельно. Переходите к [Luau](luau.md), только если приложение-хост
также намерено разрешить интерпретируемое выполнение.
