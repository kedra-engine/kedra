# Kedra и Bevy

Kedra расширяет Bevy, а не подменяет его другим движком. Компоненты, сущности, системы,
расписания, рефлексия, ассеты и плагины остаются механизмами Bevy. Kedra связывает их
с авторским контентом и рабочими процессами приложений. В workspace закреплён
Bevy **0.20.0**. Совместимость с другими выпусками Bevy и произвольными сторонними
плагинами не гарантируется.

## Что остаётся привычным

В Rust-приложении вы по-прежнему настраиваете Bevy `App` и подключаете плагины. Системы
работают с обычными ECS-данными. Экземпляр сцены становится сущностями и компонентами Bevy,
а не объектами второй ECS с отдельным планировщиком.

Система ассетов Bevy по-прежнему отвечает за загрузку, отслеживание зависимостей и метки
субассетов. Kedra дополняет этот путь проверенными поставками ресурсов и устойчивой
идентичностью исходников. Аналогично, политики компонентов Kedra используют рефлексию Bevy
для чтения поддерживаемых авторских значений, а не вводят вторую систему рефлексии.

Например, нативное приложение-хост может зарегистрировать Rust-компонент с рефлексией
под ключом схемы, загрузить сцену с этим ключом и создать её экземпляр в своём Bevy World.
Регистрация и проверка выполняются явно: добавление Rust-типа в приложение не делает все
его значения автоматически доступными в документах или видимыми в редакторе.

## Что добавляет Kedra

- **Авторские сцены и префабы:** исходные иерархии, переиспользуемая композиция,
  переопределения экземпляров и проверка до создания экземпляра.
- **Подготовка контента:** регистрация исходников, обработка и проверка поставок ресурсов
  перед использованием общими runtime-загрузчиками.
- **Основа авторинга исходников:** рабочие ревизии, проверяемые транзакции, undo/redo
  и протокол сохранения для инструментов, интегрирующих Rust API.
- **Сервисы приложений:** явная стартовая сцена, явно разрешённое выполнение Luau,
  а в debug-сборках — наблюдение за приложением, внедрение ввода и захват кадров рендерера.
- **Нативный редактор и внешние инструменты:** правки исходников с историей и явным Save,
  а отдельно — инструменты сборки, упаковки и явного запуска приложений.

Эти механизмы можно комбинировать; не каждое приложение обязано использовать их все.
Хост — Rust-приложение, настраивающее плагины, — выбирает поддерживаемые политики
компонентов, источники ассетов, адаптеры представления и возможности скриптов.

## Возможность runtime не становится автоматически функцией редактора

Runtime может создать экземпляр проверенной сцены, не предоставляя редактору права её
изменять. Rust API авторинга могут изменить рабочий исходник и подготовить запрос
сохранения, не предоставляя редактируемый Inspector или команду Save в редакторе.
Оба различия важны при изучении примеров и документации API.

Отрисовка тоже требует явной интеграции. Опциональная возможность `render` крейта сцен
добавляет создание нативного пространственного представления; загрузка данных сцены сама
по себе не подключает рендерер. Редактор поддерживает ограниченный профиль представления,
а не все графические возможности Bevy.

Luau следует той же модели. Нативный хост явно передаёт исходники программы и узкие
возможности доступа, затем разрешает выполнение. Поведения, конечные последовательности
и модули существуют, но открытие проекта или загрузка сцены не ищут и не запускают скрипты
проекта. Поддержка скриптов — не Play, не API расширения редактора и не универсальная
песочница для недоверенных нативных функций хоста.

## Различайте идентичность исходника и живое состояние

У исходного узла есть постоянная идентичность в документе; дескриптор живой сущности
принадлежит одному World и одному жизненному циклу. Два экземпляра префаба получают
разные живые сущности. Изменение живого компонента не меняет исходник префаба
и не сохраняет правку редактора.

Для поиска контента из нативного кода используйте полные логические пути, например
`game://Cuboid.prefab.ron`, через загруженный каталог источников. Такой путь обозначает
контент в пространстве имён источника, а не абсолютный путь файловой системы. Постоянные
идентификаторы остаются в исходных данных, runtime-дескрипторы — временными.

Продолжите [Картой продукта](product-map.md), чтобы проследить путь контента между этими
частями, или разделом [Загрузка и жизненный цикл](../scenes/lifecycle.md)
для подробностей интеграции сцен.
