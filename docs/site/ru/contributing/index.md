# Участие в разработке Kedra

Выберите ниже маршрут для изменения крейтов Kedra, интеграции редактора,
инструментов или документации. Для работы с продуктом начните с
[руководства](../manual/introduction/index.md). API и форматы исходников Kedra нестабильны;
полезное изменение защищает явный контракт, не выдавая будущие сценарии редактора
или игры за уже работающие возможности.

[Правила участия (English)][contributing], [правила для участников (English)][agents] и
[архитектурный контракт (English)][architecture] остаются авторитетными источниками.
Эти страницы помогают применять их, но не заменяют правила и не разрешают реализацию,
публикацию или выпуск версии.

## Подготовьте рабочую копию

Git, rustup, закреплённая версия Rust, линкер и платформенные библиотеки описаны в
[подготовке и получении исходников](../manual/getting-started/index.md).
Сохраняйте `Cargo.lock`: обычные проверки
используют закреплённое разрешение зависимостей. Первая загрузка зависимостей требует сети.
Для обычной работы над Rust не нужны частные сервисы, учётная запись ИИ или секреты доступа.

Проверкам без окна не нужен GPU. Для взаимодействия с редактором нужен рабочий нативный
рабочий стол; сборка бинарного файла не доказывает работу ввода или рендеринга.
У документации свой публичный набор инструментов, описанный в
[работе с документацией](documentation.md).

До редактирования прочитайте входные документы репозитория и README затронутого модуля
либо его модульную Rust-документацию. README есть не у каждого крейта: входом могут служить
`src/lib.rs` и связанный инженерный документ. Изучайте текущее дерево, а не только старую
ветку, поисковый фрагмент или проектное предложение.

Эти команды только читают состояние; выполняйте их из корня репозитория:

```sh
git status --short
rustup show active-toolchain
git diff --stat
```

Сохраняйте чужую работу в общей копии или дереве с незакоммиченными изменениями. Пустой
каталог результатов не означает, что существующие исходники или фикстуры можно удалять.
При совместной работе в одном дереве согласуйте принадлежность файлов.

## Опишите изменение до расширения задачи

Начните с проблемы пользователя и минимального наблюдаемого сбоя. Для сообщения об ошибке
укажите ревизию, платформу и инструменты, точные команды, ожидаемое и фактическое поведение,
а также небольшой пример воспроизведения с очищенными логами. Не раскрывайте частные
сведения об уязвимостях публично; следуйте [политике безопасности (English)][security].

Обсуждайте существенные возможности и архитектурные изменения до реализации. В предложении
укажите владельца, альтернативы, совместимость, поведение при сбое и среды проверки.
Новая зависимость не оправдана лишь тем, что сокращает один вызов. Запланированный ADR
не доказывает существование API.

Например, «устаревший кандидат docking не должен заменять текущую топологию» — это контракт
модели. Для «перетаскивание работает неправильно» нужно воспроизведение, различающее
топологию, retained-проекцию, координацию редактора и доставку нативных событий.
[Карта кодовой базы](codebase-map.md) помогает превратить симптом в ограниченное изменение.

## Пройдите один цикл изменения

1. Найдите владельца реализации, прочитайте его контракт и набор тестов.
2. Определите отказ или отклонение операции наряду с успешным результатом.
3. Выберите наименее затратную среду, способную обнаружить этот сбой.
4. Измените механизм и прямых потребителей, не оставляя дублирующего пути совместимости.
5. Вместе обновите API-документацию и затронутые английские и русские страницы.
6. Выполните целевую проверку, затем необходимые проверки для ревью.
7. Укажите фактические результаты, невыполненные проверки, нативные ограничения и риски.

Не меняйте канонические фикстуры проекта ради удобства локального эксперимента. Нативные
сценарии, изменяющие данные проекта, используют полные частные копии; см.
[руководство по тестированию][testing]. Не переносите прототипы, ассеты или
частную инфраструктуру без явного разрешения и проверки происхождения.

## Подготовьте передачу на ревью

Используйте отдельную ветку и сфокусированный запрос изменений. Объясните поведение
и выбор владельца, а не только список файлов. При необходимости дайте ссылку на задачу
или ADR, укажите влияние на совместимость, точные команды и результаты их выполнения
на рассматриваемых исходниках.

`cargo xtask check` — маршрут Rust-проверок, а не нативная приёмка или сборка сайта.
В [тестах и ревью](tests-and-review.md) описаны его этапы и отдельные проверки.
Пропущенные или прерванные проверки остаются неподтверждёнными. Локальный успех
не доказывает успех размещённого CI или действующую защиту ветки.

Публичное взаимодействие ведётся на английском в соответствии с
[Code of Conduct (English)][conduct]. Проверяйте существенную помощь ИИ, раскрывайте её
в запросе изменений и сверяйте с исходниками каждое сгенерированное утверждение.
Необязательный [поиск по репозиторию (English)][search] помогает с навигацией; он не нужен
CI и не заменяет чтение исходников или одобрение человеком.

По [правилам для участников (English)][agents] владелец должен изучить изменения и явно
одобрить их до коммита. Push, права доступа, релизы и публикация требуют отдельного
разрешения. Требования к слиянию описаны в [политике качества (English)][quality],
административные границы — в [управлении репозиторием (English)][hosting].
