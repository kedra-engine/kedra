# Контракт автоматизации приложения

Автоматизация приложения управляет доступом к диагностике, публикацией учётных данных,
операциями и захватом кадров рендерера.
Рецепты подключения и запросов находятся в [руководстве](../../manual/automation/index.md),
владение тестами и свидетельствами — в [контракте тестирования](testing.md).
[ADR 0003 (English)][adr-automation] фиксирует архитектуру.

## Композиция хоста и граница поставки

Runtime-крейт `kedra_app` не зависит от редактора и тестовых инструментов. `kedra_ui` владеет
стабильными retained-идентификаторами и геометрией рендерера. `KedraAppPlugin` устанавливает
`kedra_script::LuauPlugin`, но не исполняет код проекта и не создаёт окно/рендерер.
Хост устанавливает обычные плагины Bevy asset/input/window/render, нативные плагины и
`PrefabPlugin`. `ElementId` и `ScreenId` находятся в настоящем retained-дереве, не в тестовой
копии layout. `RemoteAppExt` регистрирует реализованные BRP-системы возможностей; повтор
имени — ошибка программиста. Стандартный набор BRP заменяется пустым списком разрешений
до регистрации: общей reflection-мутации, произвольной оболочки и загрузки плагинов нет.

Диагностический транспорт, внедрение ввода/снимки и именованные тестовые программы
компилируются только при `cfg(debug_assertions)`. Парсер поставки отвергает их флаги;
features/окружение не могут их вернуть. Обычный startup и игровой Luau остаются доступны.
Публичные структуры запросов — внутрипроцессные контракты, не схемы хранения проекта.

Хост встраивает `kedra_app::launch::LaunchOptions` в свой clap-парсер, не копирует флаги.
После установки плагинов он вызывает `cli.application.configure(&mut app, startup)`
с обычным `StartupScenePlugin`:

```rust
#[derive(clap::Parser)]
struct Cli {
    #[command(flatten)]
    application: kedra_app::launch::LaunchOptions,
    // Host-owned arguments belong alongside these options.
}
```

Release сохраняет настроенную точку входа. Debug `--scene game://Scenes/Arena.scene.ron`
меняет только путь: источники, нативные плагины и разрешение скриптов выбирает доверенный код.
Явная сцена редактора запускает одноразовый authored startup, не параллельные проектные
задачи или менеджер проектов. См.
[ADR 0030 (English)][adr-startup].
Ошибки настройки прерывают запуск, без перехода к более слабой политике.

## Аутентификация и публикация учётных данных

Только явный `transport::enable` открывает listener. Он синхронно привязывает IPv4 loopback;
нулевой порт выбирает свободный. Новый `Endpoint` содержит `url`, `session` и случайный
bearer `token`. Это полномочия пользователя приложения, не песочница ОС.
Запрос требует `Authorization: Bearer TOKEN`; сравнение постоянного времени отвергает
неверные токены. Любой браузерный `Origin`, включая локальный, запрещён. Нет привязки
публичного интерфейса, discovery без аутентификации или wildcard CORS.

Путь файла учётных данных не должен существовать, в том числе в виде символической ссылки.
В родительском каталоге готовится
временный файл с доступом только владельцу на Unix. На Windows родитель требует подходящего
ACL; транспорт его не устанавливает, нативная приёмка ACL не сертифицирована.
Включение возвращает endpoint в состоянии **pending**. Публикация без перезаписи следует после
первого цикла запроса/очистки BRP в основном World и подтверждённой инициализации HTTP runtime
и слушателя. Ошибка инициализации или появление файла назначения во время запуска запрашивает
выход приложения с ошибкой. Ни ожидающий endpoint, ни публикация не доказывают готовность функций
или нативных кадров.

Токен не передаётся аргументом CLI и не печатается средством запуска. Учётные данные, приватные
логи и необработанные наблюдения ошибок не входят в отчёты. При завершении сервер отменяется,
и приложение дожидается его остановки, не ожидая медленных соединений бесконечно. Файл учётных
данных удаляется только при успешной публикации этим экземпляром, если это обычный файл с
совпадающими session/token; подмены и символические ссылки сохраняются. Принудительно завершённый
процесс может оставить старый файл: для следующего запуска выбирайте новый путь, никогда не
перезаписывайте незнакомое содержимое молча.

## Ограничения mailbox и сервиса

Axum/Hyper/Tokio обслуживают HTTP; BRP направляет запросы в основной World, не создавая
отдельного планировщика ECS.
Транспорт имеет независимые ограничения:

| Граница | Предел / результат |
| --- | --- |
| HTTP JSON body вместе с envelope | 64 KiB; превышение — HTTP 413 |
| Параллельные авторизованные запросы | 16; превышение — HTTP 429 |
| JSON-RPC batch | 1..16 запросов; неверный envelope/batch — `-32600` |
| Ответ mailbox | Пять секунд; `-32000` сообщает неопределённость исполнения |
| Весь HTTP-запрос | Шесть секунд; HTTP 408 |
| Аутентификация / browser origin | HTTP 401 / 403 соответственно |
| Streaming `+watch` | Отклоняется с `-32601` |

Уведомление не получает обычного ответа; пакет только из уведомлений даёт HTTP 204. Пакет не
атомарен: ранние эффекты могут исполниться до последующей ошибки или внешнего тайм-аута.
Тайм-аут не означает откат. Внешний управляющий процесс обязан ограничивать запуск, время жизни
процесса и зависший цикл кадров; сопрограмма внутри приложения не может контролировать собственный
процесс.

## Операции и идентификаторы наблюдений

`app.describe` перечисляет зарегистрированные методы. Запросы с эффектами передают текущую
`session`, ненулевой UUID `id`
и, где требуется, наблюдённый живой `window`. `app.operation` принимает `{"id":"UUID"}`
и возвращает `pending`, `succeeded` или `failed` с hash/detail запроса. Повтор с тем же
ID/аргументами использует квитанцию; конфликт отклоняется без эффектов. Завершение терминально,
включая поздние/повторные завершения. Хранятся максимум 256 квитанций: старые завершённые
вытесняются первыми, активные не вытесняются. Если все места заняты активными операциями, новый
запрос отклоняется. Это не постоянный журнал защиты от повторов. При неопределённой доставке
сначала прочитайте существующую квитанцию, прежде чем рассматривать новый эффект. Успех ввода
доказывает доставку события, а не выполнение нужной функции: наблюдайте постусловие.

`app.observe` сообщает окна, нативное состояние, размеры камер, экраны, реальную геометрию UI,
видимость, доступность, фокус и редактируемые значения. Логические пиксели окна учитывают масштаб
UI и начало viewport камеры; размеры PNG выражены в физических пикселях. Повтор видимого ID
приводит к ошибке снимка; достижение предела 4096 элементов отмечает усечение. Нажатие по ID
отклоняет даже единственное совпадение в усечённом снимке. Недоступные предки и обрезанные центры
элементов приводят к отказу, но это не полное дерево доступности и не доказательство отсутствия
перекрывающего виджета.

Общие RPC window/entity ID, включая `app.observe`, остаются полноразмерными **целыми**.
В Luau native observation ID — десятичные строки. Четыре позиции редактора также возвращают
строки прямо в raw RPC; не преобразуйте их обратно в числа:

- `editor.workspace.navigation_input.viewports[*].eligible_windows[*]`
- `editor.workspace.navigation_input.viewports[*].pointer_windows[*]`
- `dock.fixture.host`
- `dock.fixture.fields[*]`

Это внутрипроцессные ID, не сохраняемые document/node ID. Клиент сохраняет точное значение
и повторяет наблюдение после замены либо изменений layout/жизненного цикла.

## Владение вводом и снимками

События указателя, удерживаемый левый `button`, сочетания клавиш, текст и запросы закрытия
проходят обычный путь ввода Bevy. Завершайте удержание отпусканием или отменой; квитанция его
не освобождает. `close_window` посылает стандартный `WindowCloseRequested` на обе нативные
поверхности событий. Хост может отказать; удаление окна может завершить итоговую квитанцию
ошибкой. Проверяйте удаление окна и успешный выход процесса вместо слепого повтора запроса.
`app.resize` допускает логические размеры 320..3840 и конечный тестовый DPR 1..4, но не меняет
физические мониторы. `editor.project` — семантический адаптер запуска, не свидетельство
клавиатурного ввода.

Захват допускается только после доставки ввода. Он ждёт минимум шесть кадров приложения и
завершается ошибкой после более 180 кадров или удаления цели; это не срок по реальному времени.
Успех требует readback рендерера, кодирования PNG и публикации без перезаписи
`<operation-UUID>.png` под `--remote-artifacts`, не имени, выбранного клиентом.
Квитанция содержит физические размеры, кадр и диагностику одноцветности. Одноцветный кадр
может быть корректным выводом приложения, но не визуальным свидетельством запуска.

Восемь ожидающих операций и восемь принадлежащих сервису нативных readback — независимые пределы.
Запросы одного окна могут делить ещё не начатый readback, сохраняя отдельные квитанции и артефакты.
Снимок, принадлежащий хосту, может предоставить readback и никогда не удаляется сервисом;
уже извлечённый старый кадр не может завершить новый запрос. Захват не активирует окно и сохраняет
фокус как целевого, так и остальных окон.

Тайм-аут или удаление цели немедленно завершает квитанцию ошибкой. Извлечённый нативный получатель
остаётся жив, пока Bevy не завершит или не освободит его; поздний результат не публикует
отменённый артефакт. Он учитывается в пределе восьми readback и после удаления операции.
Таймер не освобождает место: незавершающийся захват блокирует допуск на пределе до завершения
рендерера или перезапуска хоста. Диагностика сообщает об удержании получателей.

Внедрённый ввод/readback не сертифицирует захват указателя ОС, жесты рабочего стола, нативные
диалоги выбора файлов, настоящий IME или аппаратные переходы DPR и переходы между мониторами.
Для проверки качества нужны соответствующие ввод и кадры, а не компиляция, RPC или семантическое
изменение черновика.

## Конечные программы и внешний надзор

`app.describe.scripting` предоставляет сведения о Luau и конечных программах хоста, но не
выполнение переданного исходного кода. `app.scenario` принимает `session`, ключ идемпотентности
`id`, `scenario` и ограниченный JSON `arguments`: 64 KiB, глубина 32, целые в диапазоне точного
представления double; действует и общий предел тела HTTP. Неизвестные имена, поля source/eval,
устаревшие сеансы и пересекающиеся сценарии отклоняются. Опрашивайте существующую операцию:
допуск не означает завершение. `app.scenario_cancel` использует новый `id` отмены и UUID активной
`operation`. Отзыв полномочий не откатывает доставленный ввод, опубликованные артефакты или
изменения предметной модели.

Встроенные `app.input`, `app.resize`, `app.capture`, `app.click`, `app.field` вызывают
зарегистрированные нативные системы внутри процесса, без HTTP-запросов к себе. Последовательности
объявляют `run(ctx, args)` и используют ограниченный контекст `ctx.app`, а не глобальные API хоста.
Последовательности полей ждут фокуса, выделения, доставки текста и наблюдаемого значения.
Полномочия редактора/World не добавляются. Стандартные модули доступны только из явно допущенных
снимков исходников/конфигурации программы; поиска модулей в файловой системе, общего eval или
дополнительного тестового DSL нет. Имена типов — `AppContext`, `RuntimeContext`, `BehaviorContext`,
без префиксов совместимости.
См. [runtime contract (English)][runtime].

Ограниченный контекст `ctx.editor` предоставляет реальные `state()`/`workspace()` только для
чтения и `editor.startup.forms`: DPR 1/2, модальный фокус, Unicode, сохранение состояния при
ошибке валидации, отмену и барьеры рендерера. Внешний Rust проверяет и удаляет временные файлы;
это не эталоны изображений.
`kedra_test::Client::{input,resize,capture}` явно выбирает программы. `Client::operation`
вызывает ровно указанный нативный метод, без скрытого backend или преобразования ID.
Rust-сценарии отвечают за подготовку, проверки предметной модели и сроки ожидания процессов.
[Контракт общих инструментов (English)][test-tooling] определяет
ответственность клиента, процессов и сбора свидетельств.

## Конкретный native host и пределы свидетельств

Канонический `tests/fixtures/test_project` содержит одну обычную программу только с runtime-
зависимостями, сцены и скрипты. Полные копии изолируют сценарии; второго workspace потребителя
или отдельной цели на каждый сценарий нет. Фиксированный встроенный каталог находится вне
импортируемых ассетов. Обе независимо проверенные поставки редактора/игры обязательны как ресурсы,
но не выбирают полномочия. Загрузка данных не разрешает выполнение проекта при Open.

Его конечные `scene.switch`/`projection.exercise` и именованные программы reorder/split/activation/
maximize/visibility/restore принадлежат приложению, а не являются общим соглашением для игр.
Активация и ввод Unicode-черновика используют настоящий ввод Bevy. Внешние `native-switch` и
`native-projection` независимо проверяют состояние, идентичность retained-элементов,
рендерер/readback и жизненный цикл двух процессов. Обычное нативное закрытие должно завершить
процесс успешно: одной квитанции, которая уже могла потерять цель, недостаточно. Другие
приложения предоставляют свою проверку с
`kedra_test`. См. [native game contract (English)][native-game].

Записывайте результаты компиляции и нативных проверок отдельно для рассматриваемой ревизии.
Скриншотные проверки есть только у 22 случаев кнопок/полей ввода kit; снимки функций служат
временными барьерами GPU. Независимые идентификаторы дизайна и геометрия запуска находятся в
[визуальном контракте запуска][startup-layout], а не выводятся из снимков приложения.
[Корпус UI][corpus] хранит происхождение исходников и профиля. Публичный отчёт содержит только
проверенные переносимые свидетельства, без учётных данных, приватных логов и необработанных отказов.

## Владельцы реализации и проверки

`kedra_app/src/{lib,debug,launch,transport,operations,observe,input,capture,scripting}.rs`
реализуют эти контракты. Приватные тесты проверяют ошибки публикации транспорта, аутентификации
и mailbox, устаревшие цели ввода, владение удержанием, отказ при усечённом наблюдении,
терминальные квитанции, а также удержание получателей и позднее завершение в
`capture/lifecycle_tests.rs`. Они используют приложения без редактора и настоящий BRP mailbox,
но не проверяют нативный рендеринг. Внешние свидетельства собирают `kedra_test` и
`tools/test/src/scenarios`. Подготовка разрешённого
запуска описана в [Native scenarios](../../manual/testing/native-scenarios.md).
