# Контракт распространения приложений

`kedra_build` собирает приложения, проверяет нативные пакеты и поддерживает выпуск релизов,
не завися от конкретного приложения. Команды, требования и настройки описаны в разделах
[Сборка и запуск](../../manual/build-and-distribution/build-and-run.md),
[Упаковка и лицензии](../../manual/build-and-distribution/packaging-and-licenses.md),
[Настройка приложения](../../manual/build-and-distribution/configuration.md) и
[справочнике сборщика](../../manual/cli/build-tool.md). Эти механизмы не реализуют установленный
игровой SDK, шаблон приложения, выполнение кода проекта в редакторе или Play.

## Владельцы и граница доверия {#owners-and-trust-boundary}

| Владелец | Контракт |
| --- | --- |
| Локальный launcher проекта | Передаёт `std::env::args_os()` без изменений в `kedra_build::run_cli`; изолирует работающий инструмент в `target/kedra-build-bootstrap`, чтобы сборки Windows не перезаписали его. |
| Cargo / приложение | Владеют именем пакета, версией, единственной бинарной целью, метаданными и проверенным `Cargo.lock`. Независимые приложения сохраняют собственную политику профилей. |
| `kedra_build` | Предварительная проверка, новый staging, организация компиляции, подготовка приложения, общая проверка, явный запуск и опись пакетов. |
| `kedra_import` / `kedra_assets` | Подготовка источников и проверка поставок теми же механизмами, что у редактора; без неявной инициализации идентичности. |
| Поддерживаемый cargo-packager | Нативные bundle/форматы и платформенные помощники; не собственный установщик. |
| Приёмка редактора / CI релизов | Поведение установленного редактора, нативные машины, учётные данные и публикация; не недостающие шаги сборки. |

Этот инструментальный крейт не зависит от редактора/xtask; runtime не должен зависеть от
инструментов сборки/импорта.
`cargo xtask` остаётся проверкой репозитория, а не сборщиком приложений. Cargo build scripts
и скачанные нативные помощники выполняют код: выбранному проекту нужно доверять. `build`
и `package` не выполняют CLI/игровую логику приложения. Только явный `run` запускает приложение
после проверки. Проверка пакета может выполнять извлечение AppImage, но не игровую логику.

Закреплён cargo-packager из upstream, commit `5c1824ba8022401e9ef0de36ff1a12c5acf60237`
(версия пакета `0.11.8`), без CLI features. Upstream не закрепляет криптографически все загрузки
вспомогательных программ в кеш ОС; сборка не герметична. Обоснование зависимостей и ответственности
за безопасность — в [ADR 0023 (English)][adr23].

## Инварианты метаданных и подготовки {#metadata-and-preparation-invariants}

Метаданные Cargo выбирают ровно одно приложение. `productName` и `identifier` обязательны;
нативная версия совпадает с Cargo либо отсутствует. Пути входов относятся к каталогу пакета
и разрешаются внутри его Cargo workspace, в том числе через файловые ссылки. Обязательны
`assets`, `profile`, `namespace`, `icon` и `notices`; `license-config` необязателен.
Синтаксис полей принадлежит руководству. Общий сборщик владеет выходами, форматами,
созданными иконками и проверенными отображениями ресурсов. Непустой `packager.resources`
и дополнительные AppImage `libs`, `bins`, `files` или linuxdeploy plugins отклоняются до
компиляции: обработка произвольных ресурсов и их происхождения не реализована.
Исключения библиотек остаются настройкой нативного packager.

Build/package никогда не инициализируют и не заменяют идентичность источников. Явный
`assets init` добавляет только отсутствующие sidecars. Нативные ссылки на prefab/scene используют
полные логические пути с источником, например `editor://prefabs/button.prefab.ron`, разрешённые
через загруженный каталог с проверкой принадлежности и опубликованной ревизии; не UUID-константы
и не параллельный реестр. Сохранённые UUID, sidecars и provenance сохраняют идентичность;
логические пути ассетов не являются файловыми локаторами.

Иконки создаются из самодостаточного SVG: PNG размеров 16–1024, ICO и семейство ICNS с
плотностями 2x. Обычные Windows-сборки Cargo используют сохранённую иконку приложения;
упаковка передаёт созданные входы через окружение дочерней сборки. Build hooks компилируют
только локальные ресурсы.

Release-профиль workspace использует `opt-level = 3`, `codegen-units = 1` и `lto = "thin"`
по [рекомендациям Bevy][bevy-release]. Это увеличивает время компиляции ради оптимизации runtime,
не включает динамическую линковку разработки и не меняет debug/test-профили. Общий сборщик
запрашивает release для упаковки, но не переопределяет профили независимых проектов.

## Новая сборка и владение результатом {#fresh-assembly-and-result-ownership}

Предварительная проверка ищет нативные инструменты и настроенный сборщик лицензий до дорогой
компиляции; SDK и отсутствующие сборщики не устанавливаются. Help/version не требуют проекта
или этих инструментов. Для результатов build/run по умолчанию резервируется новый каталог внутри
каталога результатов Cargo; явный путь тоже должен быть новым. Оба варианта запрещены внутри
исходных ассетов. Предыдущие результаты не удаляются и не переиспользуются. При ошибке остаются
частичные свидетельства,
которые нельзя считать успешным дистрибутивом.

Подготовка создаёт иконки, собирает/проверяет ассеты, размещает уведомления и необязательные
исходники зависимостей, затем компилирует выбранный binary через `cargo build --locked`.
Исполняемый файл определяется по сообщениям Cargo, не угадыванием пути. macOS получает обычный
полностью подписанный `.app` без обязательного DMG; Windows/Linux — исполняемый файл с
соседними ассетами и уведомлениями.

`build-result.json` версии 1 записывает `application`, `version`, `target`, `application_root`,
`executable` и `resources`; три пути относительны к выводу. Каноническая проверка принадлежности
отклоняет обход пути и ссылки за пределы зарезервированного вывода. Результат — проверенная
передача клиенту, не настройка и не вход для старой сборки. Он записывается после проверки;
вызов package также завершает проверку пакетов до публикации этого результата.

Проверяются формат/архитектура запускаемого файла, права выполнения там, где применимо,
контрольные суммы поставки и установленные уведомления относительно staging. Linux проверяет
неразрешённые динамические библиотеки; macOS — идентичность bundle и подпись. Общая проверка
использует метаданные приложения, не команды CLI редактора. `artifact-inventory.json` и
`SHA256SUMS` следуют за проверкой реальных пакетов и связывают приложение/версию/target,
имена файлов, размеры и SHA-256. Чистый корень Git, совпадающий с Cargo workspace, даёт точную
ревизию; изменённые, вложенные или не-Git workspace записывают `source_revision: null`
и не допускаются к публикации. Хеши доказывают целостность, не личность издателя.
Одного наличия файлов недостаточно для успеха.

## Жизненный цикл явного запуска {#explicit-launch-lifecycle}

`run` использует только проверенный результат текущего вызова. Аргументы после `--` сохраняют
точные границы и Unicode. Рабочий каталог запуска — зарезервированный вывод, не исходный
checkout; launcher удаляет унаследованный `KEDRA_ASSETS` и не задаёт путь к исходникам.
Прямые дочерние процессы Windows/Linux получают закрытый stdin и постоянные
`application-stdout.log` / `application-stderr.log` в этом выводе. macOS Launch Services
открывает настоящий bundle. Закрытие launcher не предназначено для завершения приложения.
Ошибка запуска оставляет проверенную сборку на диске. Принятый запрос не доказывает
успешное завершение runtime, готовность GUI, отрисовку кадров или физический ввод;
приложение определяет свои условия готовности.

## Нативная упаковка и установленные ресурсы {#native-packaging-and-installed-resources}

Поддерживаются нативные hosts/targets Windows x64 MSVC, Linux x64 GNU и macOS ARM64/Intel;
межплатформенной установки SDK нет. Матрица редактора выбирает только Windows x64,
Linux x64 и Apple Silicon, не Intel macOS. Форматы соответственно: NSIS `.exe` и portable
`.zip`, AppImage и portable `.tar.gz`, `.dmg` с `.app`.

Нативная упаковка повторно запускает launcher из каталога манифеста приложения.
Относительные нативные настройки принадлежат этому приложению. Только дочерний процесс
получает `CI=true`, чтобы создание DMG обходилось без Finder AppleScript; окружение/CWD
вызывающего процесса не меняются. Ошибка backend, отсутствие или неверный отчёт завершают команду.

DMG использует системные дисковые инструменты; NSIS и Linux — upstream-помощники
NSIS/linuxdeploy/AppRun. Windows-проверке нужен поддерживаемый `7z` в PATH; NSIS извлекается
без запуска установщика. Временный каталог установки не изолирует реестр, ярлыки и завершение
процессов. Реальная приёмка установки/удаления принадлежит редактору и требует
`--disposable-windows-host` на одноразовом runner, не существующей установке разработчика.

Установленные ассеты размещаются в macOS `Contents/Resources/assets`, Linux
`usr/lib/<binary>/assets` для раскладки `usr/bin` либо рядом с portable executable.
Поиск не должен обращаться к CWD запуска или checkout. Редактор выбирает сначала `--assets`,
затем `KEDRA_ASSETS`, затем путь относительно executable. `kedra assets verify` без пути
проверяет этот вариант без окна; явные пути проверки также поддерживаются.
Отдельный `editor_package_smoke.py` повторно извлекает реальные пакеты и вызывает установленный
CLI без overrides из постороннего каталога. Linux использует извлечённый `AppRun`, не только
внутренний ELF. Это проверка интеграции редактора, не недостающий шаг сборки; другим
приложениям такой драйвер не нужен. Общая упаковка сначала проверяет содержимое
DMG/NSIS/ZIP/tar/AppImage.

## Нативное происхождение и материалы получателя {#native-provenance-and-recipient-materials}

Принятый GNU Linux host распространения — Ubuntu 24.04. Упаковке нужны `dpkg-query`,
`pax-utils` (`lddtree`), `tar` и каталоги copyright/common-license дистрибутива. Другим
дистрибутивам нужен проверенный адаптер происхождения. Отсутствие владельца/уведомлений/исходников
или непроверенные bundled-библиотеки блокируют упаковку. Docker на нативном x86-64 Linux нужен
для отдельной проверки перелинковки получателем, не обычной упаковки.

`licenses/native-libraries` сохраняет полные copyright-записи дистрибутива, версии пакетов/
исходников и упомянутые общие лицензии. Обнаружение принадлежит `lddtree`/`dpkg-query`.
Извлекается реальный AppImage; ELF-входы проверяются во всём AppDir, не только ожидаемых папках.
Каждой bundled-библиотеке нужен единственный записанный владелец и проверенная идентичность:
загружаемые код/данные/notes, разрешённые динамические символы и имена нужных библиотек
совпадают с оригиналом дистрибутива. Поддерживаемый парсер `object` учитывает обычные изменения
метаданных patchelf; одного совпадения имени недостаточно. Только отдельно проверенные
приложение/AppRun освобождены от сопоставления с дистрибутивом; runtime исходного комплекта —
отдельный проверенный префикс, не дополнительный ELF среди лицензионных ресурсов.
Байты установленных исходников/уведомлений должны совпадать с проверенным staging.
Допускаются только проверенные хеши уведомлений Brotli, bzip2, libffi, libpng и Wayland.
Новые условия или семейства исходников требуют проверки; сбор уведомлений не разрешает поставку.

Runtime передаётся через linuxdeploy `LDAI_RUNTIME_FILE`. Настоящий префикс образа должен
совпадать с проверенным входом, кроме стандартного 16-байтного поля `.digest_md5` appimagetool;
AppRun также имеет точную проверенную сумму. Изменившиеся upstream-загрузки отклоняются.
Оба Linux-формата включают `licenses/appimage-runtime`: закреплённые исходники runtime/libfuse/
squashfuse, upstream patch libfuse, полные уведомления, Alpine static objects/headers
и инструкции пересборки. Это материалы получателя, не ссылки на меняющиеся upstream-ветки.

Проверка получателя Docker/Meson/Make изменяет код реализации LGPL, перелинковывает и запускает
заменяющий runtime. Сохраняются настоящая карта входов линковщика и опись toolchain/пакетов;
герметичность или побитово одинаковая компиляция не заявляются. Комплект содержит лицензию
GCC startup/runtime и уведомления об исключении. Стандартные стартовые объекты компилятора
берутся из обычного toolchain получателя, не APK статических библиотек. Нативные hosted-проверки
перелинковки и установленных материалов остаются условиями релиза; наличие исходников само
по себе не доказывает полноту лицензионной приёмки.

[Обязательства перед третьими сторонами (English)][third-party] и соответствующие тексты лицензий
остаются юридическими источниками: права на изменение/отладку LGPL, точное происхождение,
MPL, исключения GCC, изменённый Winit, шрифты и графика. Этот контракт описывает свидетельства
и владельцев ошибок, не вторую лицензионную политику или юридическое заключение.

## Изоляция сборщика лицензий {#license-collector-isolation}

Настроенный `license-config` требует cargo-about 0.9.2. Сбор лицензий нативных normal-зависимостей
отклоняет неразрешённые лицензии, создаёт полные copyright/license notices без локальных путей
и включает оригинальные `.crate` MPL-зависимостей crates.io с проверкой по `Cargo.lock`.
Неизвестное non-registry происхождение отклоняется, а не подменяется registry-исходниками.
Это дополняет, не заменяет политику допуска зависимостей cargo-deny и юридическую проверку.

В закреплённом TLS-графе сборщика лицензий есть предупреждения об уязвимостях; зависимость krates
его библиотеки закрепляет indexmap/petgraph несовместимо с workspace. Не понижайте зависимости
приложения, не патчите upstream и не добавляйте крейт-обёртку ради интеграции. Явный общий
установщик использует upstream-исходник с закреплённой суммой, обновляет отдельный lockfile,
проверяет его через Cargo/cargo-deny до компиляции и устанавливает именно этот граф с `--locked`.
Исходники, lockfile и результаты сборки остаются вне любого Cargo workspace; lockfile служит
свидетельством, а не вторым отслеживаемым lockfile приложения. Существующие каталоги никогда не
перезаписываются. Графы могут различаться в зависимости от даты установки; каждая установка
проходит аудит. CI использует `RUNNER_TEMP` и сохраняет разрешённый lockfile инструмента.
Нет Python-установщика или неявной настройки при сборке; команды установки описаны в руководстве.

## Приёмка независимого потребителя {#independent-consumer-acceptance}

`tests/fixtures/distribution` — отдельное приложение Cargo, не игровой runtime или опубликованный
шаблон. Помощник копирует его в изолированный workspace со своим lockfile и локальным launcher:

```sh
python3 -X utf8 tools/distribution/validate_fixture.py --package
python3 -X utf8 tools/distribution/validate_fixture.py --revision EXACT_PUBLIC_GIT_SHA --package
```

Это проверки с нативным выполнением, не команды проверки документации. Локальные и закреплённые
публичные Git-источники выбираются явно; local-path запуск не доказывает потребление из Git.
Помощник сохраняет xtask alias, создаёт иконки/sidecars, использует общий маршрут build/package
и запускает runtime-потребителя из staging. Normal-граф запрещает зависимости editor/import/
build-tool. Также проверяется `cargo kedra run` с ожиданием маркера приложения после того,
как независимо запущенный runtime проверит свою поставку.

## Граница организации релиза {#release-orchestration-boundary}

Запускаемый вручную [workflow Desktop distribution][release-workflow] допускает только защищённую
`main`, точный SHA исходников и новый тег, совпадающий с версией Cargo. Предварительная проверка
требует, чтобы выбранная ревизия входила в историю защищённой main, CI репозитория действительно
успешно выполнился по событию push на этом точном SHA и был доступен текущий результат
GitHub Actions `CI required`. Существующие теги и релизы приводят к ошибке и не перезаписываются.
Дерево `.github/workflows` выбранных исходников должно совпадать с текущей веткой по умолчанию
до сборки и при публикации: для других деревьев могут понадобиться права записи workflow,
недоступные обычному токену Actions. Нельзя обходить это ограничение личным токеном или
расширением прав.

Три нативных исполнителя используют общую команду и независимое приложение-потребитель,
получающее исходники из закреплённой ревизии публичного Git-репозитория. Независимый от целевой
платформы аудит зависимостей приложения выполняется один раз на Linux; все исполнители
устанавливают cargo-deny для аудита изолированного графа сборщика лицензий. Общие регрессионные
проверки архитектуры, подписи и упаковки принадлежат `kedra_build` и выполняются в нативном Rust CI;
Python отвечает за дымовые проверки редактора. Linux CI явно запускает проверки исходного
комплекта и перелинковки изменённого LGPL-кода при изменении входных данных упаковки, а не при
каждом релизе. Каждая целевая платформа релиза всё равно проверяет реальные пакеты и потребителя
публичных Git-исходников: эти проверки охватывают разные артефакты и поведение установленного
приложения.

Кеши содержат только зависимости, отделены от кешей проверок и покрытия и ограничены
`target/distribution-cargo` и изолированным каталогом сборки средства запуска. Итоговые пакеты
и workspace независимого потребителя находятся во временном хранилище исполнителя вне кешей.
Уже существующий каталог результатов приводит к ошибке даже при прогретой сборке. Задачи сборки
и проверки пакетов имеют права только на чтение репозитория. Пакеты хранятся один день;
ограниченные диагностические данные и lockfile инструмента — три дня. Python использует
стандартный режим UTF-8 и в Windows; Unicode-пути нельзя удалять ради старых консольных кодировок.
Проверки архитектуры разбирают настоящий скомпилированный исполняемый файл через `object`, проверяя
как совпадающую, так и несовпадающую целевую платформу; имя файла или успех CLI недостаточны.

`publish` по умолчанию false: приёмка сборки не публикует релиз. Только итоговая задача публикации
получает `contents: write`. Она не получает рабочую копию исходников приложения и не собирает его,
а загружает только необходимые файлы правил из неизменяемой ревизии workflow ветки main,
заданной точным SHA. Она требует успешного завершения нативной матрицы этого запуска,
подтверждённого планировщиком, использует только артефакты этого запуска и проверяет размеры,
хеши и идентичности исходников всех пяти публикуемых файлов. Затем создаёт новый черновик релиза,
проверяет полный набор загруженных файлов и их серверные хеши, связывает тег с проверенными
исходниками и публикует предварительный релиз, явно обозначенный как неподписанный.
При ошибке черновик остаётся неопубликованным; повторные запуски никогда не заменяют его.
REST-запрос создания черновика возвращает числовой ID релиза для проверки и публикации; поиск
по тегу предназначен только для опубликованных релизов, а не для обнаружения черновиков.
Поддерживаемый GitHub CLI передаёт файлы; обновление по ID снимает `draft` только после проверки
размеров и хешей. Протокол определён в [правилах релиза][release-policy].

## Подписи, обновления и границы приёмки {#signing-updates-and-acceptance-limits}

У prerelease macOS `v0.1.0` известен дефект подписи bundle; нужна локальная переподпись.
Новые bundle по умолчанию полностью подписываются изнутри наружу ad-hoc (`-`), сохраняя явно
настроенную identity. Все ресурсы и `Info.plist` запечатаны до создания DMG. Проверка копирует
приложение из реального образа и выполняет `codesign --verify --deep --strict --verbose=2`
до отдельной приёмки CLI редактора. Это не Developer ID и не notarization; Windows-пакеты
остаются неподписанными. Проверка целостности не подтверждает доверие Gatekeeper/SmartScreen.
Никогда не отключайте защиты ОС глобально; обычное разрешение macOS всё ещё может понадобиться.

Нативные пакеты редактора несут идентичность установки для `kedra_update`; portable-сборки
и другие приложения не должны случайно получать её. Host владеет разрешением обновления,
урегулированием ввода/документов и завершением; запись установки никогда не сохраняет источники
проекта. Явная замена macOS и ручная обработка NSIS/AppImage описаны в
[контракте update crate (English)][update]. Нативная приёмка обновлений отдельна и ещё ожидается.

macOS 15 — настроенный минимум редактора. Зависимости Linux glibc/GPU, минимум Windows,
установка/удаление и каждая архитектура ещё требуют нативной приёмки. AppImage не делает glibc,
видеодрайверы или FUSE универсально совместимыми. Проверки подписи, установленного CLI/ресурсов,
кадров, физического ввода и интеграции ОС — разные свидетельства. Текущая публичная доступность
`v0.1.0` требует внешней проверки. Автоматический draft-to-published путь, текущие нативные пакеты/
ресурсы и перелинковка получателем остаются непроверенными; исходники workflow не доказывают
hosted-приёмку, успешную публикацию или полноту лицензионной приёмки.
