# Работа с документацией

Изменение документации меняет публичный контракт. Пишите о том, что доступно читателю
в текущей реализации, отличайте планы от работающих путей и сохраняйте факты о безопасности,
лицензиях и происхождении материалов. [План документации (English)][plan] определяет
границы миграции, а [инфраструктура документации (English)][infrastructure] — актуальные
инструменты и локальные команды.

## Выберите правильный раздел

| Раздел | Задача читателя | Чего избегать |
| --- | --- | --- |
| Руководство | Понять/использовать существующие сценарии продукта | Организация всех глав по крейтам |
| Участие в разработке | Менять Kedra с правильным владельцем и свидетельствами | Полное копирование правил репозитория |
| Rust API docs | Точные типы, методы, инварианты, отказы и жизненный цикл | Замена API-контрактов учебником |
| ADR | Долговременные решения, альтернативы и критерии проверки | Представление предложений как реализации |
| Дорожная карта | Явные будущие задачи и критерии завершения | Описание целей как текущих возможностей |
| Документация крейта/модуля | Локальная ответственность, features, примеры и ошибки | Несопровождаемые конкурирующие авторитетные копии |

Описывайте API изменения исходников, не выдавая их за визуальное сохранение в редакторе:
общее визуальное редактирование документов, публикация новых файлов и Play ещё не реализованы.
Доступны только описанные изменения исходников через Inspector и Save существующего документа.
Макет Figma — источник дизайна,
а не скриншот реализованного UI.

## Проверяйте утверждение до написания рецепта

Прочитайте текущую реализацию владельца и его manifest/features, затем изучите нужные тесты
или реальный CLI-парсер. Проверьте флаги, необходимые ресурсы и отказы. Прочитанное утверждение
теста ещё не означает, что тест выполнен; прежний запуск не проверяет текущую ревизию
с изменениями. Явно фиксируйте ограничения, не опускайте их молча.

Для внешних API изучите `Cargo.lock` и точный разрешённый исходник/версию. Запрашивайте
определяющий Bevy subcrate, а не только фасад. Git-патчи и платформенное поведение требуют
исходника, если внешняя документация не соответствует ему. Необязательный поиск по
репозиторию помогает найти свидетельства, но не делает непроверенный фрагмент авторитетным.

Указывайте рабочий каталог команд и предварительные условия. Различайте полный исполняемый
пример и фрагмент, которому нужна окружающая подготовка. Сохраняйте точные идентификаторы;
не выдумывайте мутации фикстур или новую тестовую инфраструктуру ради видимости готового
примера. Подсветка RON как Rust не проверяет схему.

## Поддерживайте английский и русский вместе

Английский — канонический язык. Парные страницы находятся в `docs/site/en/` и `docs/site/ru/`
по одинаковым относительным путям с английскими slugs. Переводите объяснения, заголовки,
подписи и навигацию естественно; команды, пути, API и фактические подписи UI не меняйте.
Например, пишите «панель Hierarchy», а не придумывайте перевод имени элемента.

Обновляйте обе версии в одном рассматриваемом изменении. Сверяйте предварительные условия,
ограничения, отказы и границы свидетельств в обоих языках. Наличие парного файла не доказывает
качество перевода. Для повторяющихся терминов используйте общий
[глоссарий](../manual/glossary.md), добавляя английский термин там, где он проясняет смысл.

Для существующих статей сайта используйте относительные `.md`-ссылки соответствующей локали.
На контракты вне сайта, ADR и оригиналы provenance ссылайтесь через URL репозитория;
на русских страницах помечайте такие переходы English. Не копируйте инженерный документ
на сайт лишь ради видимости перевода. Rustdoc первоначально остаётся на английском.

## Проверяйте текст и ссылки, не смешивая сборки

Закреплённые версии Node/Bun, установка без изменения lockfile, генерация сайта и preview описаны
в [справочнике инфраструктуры (English)][infrastructure]. Для нативной сборки редактора
инструменты сайта не нужны.

Из `docs/` команда `bun run build` не требует Rust и включает парный справочник Luau.
`bun run build:api` дополнительно запускает Cargo и включает сгенерированный английский
rustdoc; см. [руководство API](../api/index.md). Этот явный локальный маршрут не меняет CI.

Если закреплённые инструменты уже доступны, из корня репозитория можно выполнить:

```sh
rumdl check docs/site/en/contributing docs/site/ru/contributing
lychee --offline --include-fragments --no-progress \
  --root-dir "$PWD/docs/site" \
  docs/site/en/contributing docs/site/ru/contributing
node docs/scripts/check-locales.mjs
```

Замените пути lint/link-проверок на изменённый раздел. Проверка локалей охватывает все пары
сайта и проверяет наличие, а не смысловое соответствие. Offline-проверка ссылок не проверяет
удалённые URL репозитория или текущую доступность сервисов. Для навигации и anchors
сгенерированного HTML нужен отдельный build/link-маршрут из справочника инфраструктуры.

До приёмки выполните необходимые полные проверки; целевая проверка текста сама по себе
не является сборкой сайта, rustdoc, Rust-проверкой или результатом нативного взаимодействия.
Сверяйте примеры кода с их реальными владельцами: Markdown lint не компилирует фрагменты
и не валидирует исходные данные.

По правилам роста репозитория авторские текстовые файлы не должны превышать 1000 строк
и 64 KiB. По возможности удерживайте прозу в 100 колонках; таблицы и код могут быть шире.
Делите по связной ответственности, а не на номерные части, не минифицируйте и не вводите
новые исключения.

## Сохраняйте происхождение материалов и границы миграции

Для нового текста, медиа, примеров кода и эталонных кадров нужно подтверждённое право
вклада. Сохраняйте лицензии и проверенные идентификаторы источника дизайна.
[Руководство по сторонним компонентам (English)][legal] и
[контракт визуальной приёмки][visual] остаются авторитетными; переводы
не заменяют оригиналы лицензий. Помощь ИИ не снимает обязанности проверки с участника.

Пишите о возможностях и задачах читателя, а не об истории подготовки страницы. Страницы,
не являющиеся планами, описывают текущие факты, контракты и ограничения, а не
расшифровки сеансов, промежуточные попытки или число прежних успешных запусков.
Храните свидетельства в `target/`, а фактическую проверку резюмируйте при передаче на ревью.
Планы и предложенные ADR могут описывать будущее только отдельно от реализации.

Мигрируйте постепенно. До удаления старого документа учтите все живые контракты,
ограничения, provenance и правовые обязательства, проверьте оба нужных языка и обновите
входящие ссылки/anchors. Сохраняйте стабильные публичные URL там, где они уже опубликованы.
Не переименовывайте устаревшее описание реализации в план и не оставляйте две конкурирующие
авторитетные копии. `CONTRIBUTING.md`, `AGENTS.md` и сохраняемые источники репозитория не
подлежат этому удалению; [каталог контрактов](contracts/index.md) указывает опубликованных
инженерных владельцев.

В конце проверьте путь читателя: сможет ли участник найти владельца, выполнить шаг и понять,
что ещё не проверено? Артефакты preview сайта — не публикация. Хостинг, права, снимки релизов
и публичное размещение требуют отдельного одобрения. Передача свидетельств описана в
[тестах и ревью](tests-and-review.md).
