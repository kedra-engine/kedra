# Архитектура и изменения

[Руководство Rust API](../api/index.md) объясняет просмотр сгенерированных контрактов;
[обзор Luau API](../api/luau/index.md) разделяет runtime и области под управлением хоста.

Определите владельца изменения, его потребителей и поведение при отказе.
Найдите владельца по [карте кодовой базы](codebase-map.md), затем прочитайте
[архитектурный контракт (English)][architecture] и соответствующие ADR. Проверяйте статус
каждого ADR: предложенные взаимодействия редактора — не готовые API и не разрешение
реализовывать их.

## Расширяйте механизм, уже отвечающий за гарантию

Перед добавлением инфраструктуры найдите существующие решения в репозитории и среди
поддерживаемых инструментов экосистемы. Сравните совместимость, сопровождение, лицензию,
безопасность и стоимость зависимостей. Bevy владеет ECS, отражением, планированием и
ассетами; Kedra использует обычные крейты и плагины, а не параллельные ECS, DI-систему,
планировщик или собственный язык UI.

Например, изменение допуска поставки ресурсов должно использовать существующую границу
assets/import, а не вводить отдельный валидатор редактора со второй политикой допуска.
Выбор исходника принадлежит адаптеру редактора, а не независимым от потребителя отражённым
значениям. Прежде чем переносить API, проследите текущий путь отказа и его потребителей.

Если подходящего поддерживаемого решения нет, опишите конкретный пробел и необходимость
собственного ограниченного кода. Одних «правил Kedra» недостаточно для переписывания
парсера, обходчика или запуска процессов, чья механика уже имеет поддерживаемого владельца.

## Решите, нужен ли новый крейт

Держите связанную ответственность вместе. Выделяйте механизм, если у него самостоятельная
цель, небольшой полезный API, реальный потребитель и корректное место в DAG. Одного
потребителя достаточно; гипотетическое повторное использование не обязательно. При этом
не создавайте пустой forwarding-крейт, спекулятивный фреймворк или пронумерованные части
только ради размера файла.

Например, `kedra_script` управляет сроком жизни VM и областями доступа, а `kedra_script_bevy` —
опциональной интеграцией Transform/виджетов. Редактор предоставляет собственный workspace API
и разрешает выполнение. Перед расширением этой границы
прочитайте [контракт крейта bindings (English)][bindings].

Предложение о границе должно отвечать на вопросы:

- Какими значениями и ресурсами владеет механизм и когда они освобождаются?
- Что приложение разрешает, планирует или показывает самостоятельно?
- Какой production-потребитель использует API сейчас?
- Какой слой и какие зависимости нужны, включая build/optional/target-зависимости?
- Какие публичные ошибки и гарантии неизменности состояния будут наблюдать тесты?

Сохранение независимого механизма внутри приложения тоже требует обоснования. Не
превращайте редактор в крейт для всего лишь потому, что он оказался первым потребителем.

## Проверьте объявленную границу зависимостей

Разрешённые слои назначения:

| Исходный слой | Допустимые слои назначения |
| --- | --- |
| `core` | `core` |
| `runtime` | `core`, `runtime` |
| `authoring` | `core`, `runtime`, `authoring` |
| `import` | `core`, `runtime`, `authoring`, `import` |
| `editor` | `core`, `runtime`, `authoring`, `import`, `editor` |
| `tooling` | Все объявленные слои |

Каждый участник объявляет `package.metadata.kedra.layer`, наследует workspace lints
и использует `MIT OR Apache-2.0`. [Архитектурная проверка (English)][gate] читает Cargo
metadata и манифесты; опциональность, переименование и неактивная платформа не скрывают
запрещённую зависимость. Особое ограничение Inspector описано в
[карте кодовой базы](codebase-map.md).

Эти правила проверяет `cargo xtask architecture`. Успех не доказывает изоляцию возможностей
runtime: проверка исключает dev-зависимости и не изучает смысл кода внутри пакета.
Runtime всё равно не должен зависеть от редактора, импортера и файлового writer исходников.
Не обходите это слоями совместимости, лишь перенаправляющими вызовы.

## Проектируйте публичный API вместе с жизненным циклом

Документируйте инварианты, ошибки, владение и жизненный цикл там, где определяется API.
Разделяйте подготовку и публикацию, отмену и завершение; указывайте судьбу устаревшей работы.
Файловый commit, authoring-транзакция и отложенная ECS-мутация дают разные гарантии;
не обещайте общий rollback для всех трёх.

Например, подготовленный docking-кандидат принадлежит конкретной ревизии workspace.
API, получивший устаревшего кандидата, должен отклонить его без замены опубликованной топологии.
Для асинхронных задач приложения определите поколение/владельца, позволяющего отвергать
неактуальное завершение, а не только успешный результат задачи.

Нативные ссылки на сцены/префабы используют логические пути с источником, например
`editor://prefabs/button.prefab.ron`. Разрешайте их через существующий загруженный каталог
с проверкой принадлежности и опубликованной ревизии. Не добавляйте жёстко заданные UUID
документов или параллельный реестр поиска. Сохранённые ID, sidecars и provenance сохраняют
UUID-идентичность; логический путь поиска — не файловый локатор и не новая идентичность.

Исходники владеют Save. Состояние runtime, черновики и производные поставки остаются
разделёнными. Загрузка сцены не разрешает выполнение скриптов. API изменения исходников
не означает наличие общего визуального редактирования, Save в редакторе или Play.
Реализованы только описанные изменения исходников через Inspector и Save существующего документа;
общее редактирование и Play пока недоступны.

## Проверьте features, безопасность и совместимость

Обосновывайте новые публичные API и зависимости. Изучайте точные разрешённые версии и
включённые features, а не только документацию последнего upstream-релиза. Для Git-патчей
нужен разрешённый исходник. Корневой манифест сейчас закрепляет Bevy и патчит Winit;
перед использованием внешнего API сверьтесь с lockfile и
[руководством по сторонним компонентам (English)][third-party].

Одного `--all-features` мало для проверки default, minimal и платформенного поведения.
Выполняйте нужные feature/consumer-маршруты; взаимоисключающие features или новые
платформенные обязательства требуют ADR и изменения CI-матрицы. `cargo xtask features`
содержит отдельные minimal runtime-проверки и тесты границы диагностики с отключёнными
debug assertions, а не оптимизированный релиз редактора или нативную приёмку.

Unsafe запрещён в коде workspace. Локальное отключение lint не является исключением;
изменение правил требует ADR, рассмотренного обоснования безопасности и подходящих Miri-тестов.
Сохраняйте Unicode и платформенную семантику путей. Не показывайте абсолютные файловые пути
в подписях ассетов проекта, не меняя сохранённую идентичность и нативные локаторы.

Завершите проект [планом тестов и ревью](tests-and-review.md), перечнем затронутых документов
и явных нецелей. Долговременные сквозные решения оформляйте в ADR, а не только в обсуждении.
